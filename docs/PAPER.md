## Abstract

LordOS is a free GNU/Linux distribution based on Debian 13 that ships a desktop environment of its own, built from its fundamental components on top of Debian and Wayland. Instead of GNOME or KDE, it has its own display server and Wayland compositor written in C (`lord-server`), its own user-interface engine (React running on the QuickJS JavaScript engine, with layout, painting and text in native C code), its own native apps, and its own security services: an app sandbox launcher, a permission broker, a per-app permission store, a kernel-enforced per-app firewall, package signing and an encrypted password vault. It reuses what is mature and widely reviewed: the Linux kernel, Debian and its packages, Mesa, PipeWire, the Wayland protocol, Xwayland for X11 apps, and a handful of libraries (FFmpeg, Poppler, libarchive, OpenSSL, libsrtp2, usrsctp, libfreerdp, Monocypher and, since 0.8.8.6, Tesseract and audio.cpp with its ggml; in 0.8.8.8, also PipeWire's client library, nanosvg and, in an optional package, WPE WebKit) that are confined to small sandboxed helper processes, to the session manager or, for WPE WebKit, to the web app runtime `lord-web`.

This paper describes the design and the current state of LordOS as it stands in the repository on 22 November 2026, for a technical reader who wants to check the project rather than take it on trust. **The latest release is 0.8.9.4 Beta** (20 November 2026), the fourth update of 0.8.9 Beta (18 November 2026, with new images) through Store → Updates and `apt`; 0.8.9 is also reached from 0.8.8 the same way; the 0.8.8.10 pre-release that some of its work was first built for never shipped. 0.8.0 (18 October) was the first public release, followed by 0.8.1, 0.8.2, 0.8.3, 0.8.4, the package-only 0.8.4.1, 0.8.5, 0.8.6, 0.8.7, 0.8.8 (2 November), its updates 0.8.8.1 to 0.8.8.9 through the Store and `apt`, 0.8.9 (18 November) and its updates 0.8.9.1, 0.8.9.2 (19 November), 0.8.9.3 and 0.8.9.4 (20 November), each listed in `CHANGELOG.md`. ## 1. Vision

### 1.1 The problem

A modern Linux desktop is assembled from many independent projects: a display server or compositor, a toolkit, a session manager, a settings daemon, a keyring, a network manager, a firewall front end, and the apps. Each is good on its own terms, but the seams between them are where things get slow, inconsistent or insecure. Three seams in particular motivated LordOS:

- **Weight.** A desktop that draws its shell with a web engine, or loads several toolkits at once, needs hundreds of megabytes before the user opens anything. LordOS wants to be comfortable on modest machines and on a Raspberry Pi 5.
- **Trust in apps.** On a traditional Linux desktop, every program the user runs can read the whole home folder, record the microphone, open any network connection and read the clipboard. Sandboxing exists, but it is usually an add-on that the desktop itself doesn't understand.
- **Visibility.** Users rarely see which app is talking to which server, and even more rarely can they say "this app may not use the internet" in a way the app can't get around.

### 1.2 Principles

The project follows a short list of rules, written down in `AGENTS.md` and `docs/ARCHITECTURE.md`:

1. **Own the parts the user touches; reuse the foundations.** The display server, the compositor, the UI engine, the apps and the security services are LordOS's code. The kernel, Debian's packages, Mesa, PipeWire and the Wayland protocol are reused.
2. **A strict dependency policy.** X11, wlroots, libdrm, libinput, WebKit, GTK and Qt are not used inside LordOS. Libraries that parse untrusted data are linked only by sandboxed helpers, never by the compositor.
3. **The interface can't run commands.** JavaScript in LordOS has no API to execute arbitrary programs. The exceptions are few, narrow and each approved and documented in `AGENTS.md`: the Terminal's login shell; launching an installed `.desktop` app (optionally with one file the user opened, or one of the app's own named actions); starting an installed `.lpk` app in its sandbox; Xwayland, started by `lord-server` itself with a fixed command line only when an X11 app connects; the components' network connectors and the blocklist downloader, which re-execute LordOS's own binaries with fixed arguments; the Store's download child, which places itself in its own scope; and, in 0.8.7, the remote folders: `lord-server` starts `rclone mount`, `ssh-keyscan`, `openssl`, `rclone obscure` and `fusermount3` in a scope of their own, with no shell, and a checked address goes on as data (§6.7); and a packaged app's companion, one binary a Verified author signed, in a root-owned folder, hashed through the descriptor that then runs it, in a sandbox of its own, with no path or argument from the app (docs/PACKAGED-APPS.md); in 0.8.8.5, Cloud: `lord-server` runs rclone's remote control on a Unix socket only, in a scope of its own, and can send it only a fixed table of 28 methods, so nothing in LordOS can ask it to run a command (`docs/CLOUD.md`); and, since 0.8.8.6, `lord-say`, which `lord-server` starts from the fixed path next to it to read text aloud, with fixed arguments, the text on its input as a sealed memory file and never in its arguments, every other descriptor closed, and nothing chosen by JavaScript but a voice name checked in C (§6.7); and, since 0.8.8.7, the Terminal's Files mode, which runs no program at all: `lord-server` opens channels on the tab's own `ssh` connection-sharing socket with OpenSSH's multiplexing protocol, for an `sftp` session and a closed list of remote commands whose arguments are checked in C (§5.1, §6.7); in 0.8.8.8 its port forwards, the files dropped on an `ssh` pane and the downloads from an `ls` listing go through the same socket and run no program either. In 0.8.8.8 two more: a `.desktop` app marked `Terminal=true` runs nothing when it is launched, since `lord-server` keeps its parsed `Exec` in a one-shot slot (a random 128-bit token, 10 s, used once) and types it, quoted in C, into a new Terminal tab's login shell, so JavaScript only ever holds the token; and `lord-web`, the web app runtime, which only `lord-server` starts, from the fixed path next to it and with exactly `--app <app> --profile <profile>` (and `--inspect` last for a window with developer tools, only while developer mode is on), both checked against the registry (§5.4). None takes a command from the interface.
4. **Root only through closed doors.** Everything that needs root goes through a fixed table of validated actions or a small dedicated service with a closed protocol.
5. **The CPU path must always work.** GPU composition is an optimization, never a requirement.
6. **The compositor never waits.** Helpers, apps and services talk to `lord-server` over non-blocking sockets; a hung app hangs only itself.
7. **Verify on a real system.** Every milestone is checked on a virtual machine with real screenshots before it is marked done, and compatibility that wasn't tested isn't claimed.

## 2. Architecture

### 2.1 Layers

**Figure: The layers of LordOS.**

```
Apps
    Built-in apps and the theme · isolated .lpk apps · Linux apps (GTK, Qt, browsers; X11 apps through Xwayland)
        │
LordOS UI engine
    React on QuickJS, native layout, painting and text in C. Used by LordOS's own apps; Linux apps don't go through it
        │
LordOS display server and Wayland compositor
    lord-server, in C: KMS without libdrm, evdev without libinput, composition on CPU or GPU. Linux apps and isolated .lpk apps connect here as Wayland clients
        │
Debian 13 userland
    dpkg and packages, Mesa (optional GPU), PipeWire, libwayland, libxkbcommon, systemd
        │
Linux kernel
    DRM/KMS, evdev, Landlock, seccomp, cgroups v2, eBPF
```

*Violet layers are LordOS's own code; the lower layers are reused from Debian and Linux.*

From the bottom up:

- **The Linux kernel** provides DRM/KMS for displays, evdev for input, and the security features LordOS builds on: Landlock, seccomp-bpf, cgroups v2 and eBPF. On PCs it is Debian's kernel; on the Raspberry Pi 5 it is LordOS's build of the Raspberry Pi kernel with Landlock enabled (§7.4).
- **Debian 13** provides the userland: `dpkg` and the package archive, systemd, Mesa, PipeWire, `libwayland`, `libxkbcommon`, CUPS, BlueZ and the rest.
- **`lord-server`** is the display server and Wayland compositor. It drives displays and input directly, composites, and serves the Wayland protocol to Linux apps.
- **The UI engine** lives inside `lord-server`: QuickJS runs the React interface, and native C code does layout, painting and text.
- **Apps** come in four kinds: built-in apps and the theme, which run in `lord-server`'s JavaScript context; installed `.lpk` apps, each in its own sandboxed process with its own engine instance; Linux apps, which connect to the compositor as ordinary Wayland clients; and web apps and PWAs (0.8.8.8), run by the LordOS Web Runtime in `lord-web`: each window, one per app and profile, is its own process, the page runs under WebKit's own sandbox, and no LordOS API (`lord.*`, the broker) reaches it. LordOS runs those web apps unmodified: it doesn't change them, it only runs them (§5.4).

### 2.2 Processes and privileges

**Figure: Processes and privileges.**

```
Sandboxed app processes
    lord-server --app <id>: one per .lpk app, and Passwords, Mail, Calendar, Contacts and Reminders; Landlock, seccomp, cgroup
        │
Sandboxed helpers
    lord-doc, lord-media, lord-maild, lord-vault, lord-fetch: no sockets, no exec, files only as descriptors
        │
lord-server (one per user)
    Runs as the user: compositor, UI engine, broker; no command execution
        │
Root services with closed interfaces
    lord-sessiond, lord-netd, lord-netperm, lord-fand, and the admin helper's fixed action table
        │
Linux kernel
    Enforces Landlock, seccomp, cgroups and the firewall's eBPF programs
```

*Privilege goes down the stack; each layer talks to the one below only through a narrow, validated interface.*

A running LordOS system has a small number of processes with clearly separated roles:

|---|---|---|

### 2.4 System services

- **Network (`lord-netd`).** The network belongs to the system, not to a session. `lord-sessiond` starts `lord-netd` at boot with a fixed path and no arguments, so the machine has an address before anyone logs in. It runs only the closed `net-*` actions: its own DHCP client and netlink code, Wi-Fi through Debian's `wpa_supplicant`, WireGuard through LordOS's own netlink code, OpenVPN, IPsec/IKEv2 through strongSwan's `charon` driven over VICI with LordOS's own client, and optionally OpenConnect, PPTP and Fortinet-compatible tunnels. It talks only to the sessions' root helpers, over a socket that accepts only uid 0.
- **Fans (`lord-fand`).** A root service that reads the CPU temperature every 2 s and writes fan duty from a profile, from early boot. It drives only fans its own scan found: the Raspberry Pi 5 fan header and allow-listed motherboard controllers. Laptop, GPU and unknown fans are never written. On stop, or after a crash, it restores the original kernel settings. It runs no programs, has no network, no capabilities and no device nodes.
- **Hardware settings.** Displays (modes from KMS with EDID names, a 15-second "keep these settings?" revert, per-display persistence, rotation, Night Light), Bluetooth through BlueZ, battery and power profiles, idle and lid handling, date and time, notifications for Linux apps and default apps (since 0.8.6: when you haven't chosen one, a file opens with the system's default or the first installed app that declares its type, shown as "Automatic"). Changes arrive as kernel uevents and D-Bus signals; nothing polls. On a Raspberry Pi 5, Settings → Board firmware shows and updates the bootloader in the board's EEPROM through two closed admin actions (0.8.4.1). **In 0.8.9:** *Settings → Battery*, for any laptop and every theme, through the kernel's standard `power_supply` attributes and no vendor tool (`docs/BATTERY.md`): the state, the daily use of the last 8 days and the level by hour, screen time on battery, an estimate per app from each app's CPU on battery, the battery's condition, capacity and cycles (counted by LordOS when the battery reports none), and optimized charging (a charge limit, a "plug in" notice, pause charging, heat protection at 40 °C, discharge on power). The history is kept by `lord-server` in `~/.local/state/lordos/battery-history` and never sent anywhere; the charging is changed only by an administrator, through two new closed admin actions (§6.3), and what the laptop can't do shows disabled with why. Monitor gains live Battery and Devices tabs, and the battery in the bar opens every device's battery: the computer's, mice and keyboards (with `lord-hidpp` for Logitech devices, §6.7) and Bluetooth headphones. Not yet tested on laptop hardware. *Laptops that woke a second after going to sleep with the lid open* (GitHub #172: the firmware's lid device is a wake source that fires although the lid never moved) get a systemd-sleep hook, `lordos-lid-wake`, that turns that wake source off before sleep and back on after, only on a portable chassis with every lid open (§6.3); tested in `build/lidwake-test`, not yet on the reporter's laptop. *Displays:* with nothing saved, a display uses its EDID's preferred mode only when its shape is within 8 % of the panel's physical one, else the largest mode of the panel's shape, so an ultrawide no longer opens stretched at 16:9 (#173). *Wi-Fi:* Settings → Network lists the network LordOS is connected to first, with Disconnect, and manages saved networks (#167), with no new admin action. *In 0.8.9.1:* the Control Center's Wi-Fi tile switches Wi-Fi with the same closed `net-up`/`net-down` actions and shows the connected network's name, which `lord-server` reads without root from nl80211 (#192).
- **Updates.** Installed systems update in place from LordOS's signed APT repository on lordos.org, from Store → Updates or with `apt`; changes that are more than new files run as numbered, idempotent migrations (0.8.1). The Store's package engine follows apt's priorities (`/etc/apt/preferences.d`, 0.8.5), so on the Raspberry Pi image "Update all" chooses the same versions as `apt` and the pinned kernel stays blocked, and it accepts sources written as `Architectures: amd64,arm64` as apt does. The update from 0.8.4.1 or 0.8.4 to 0.8.5 runs no migration; it was tested with the release package built as 0.8.5~rc2 on a VMware machine on 0.8.4.1 and a Raspberry Pi 5 on 0.8.4, both with `apt`, then a restart. The update from 0.8.6 to 0.8.7 brings `lordos-hwdata`, a new dependency from the same repository, and migration 006 (the login screen's `render` and `video` groups and, on the Pi, the pin on its FFmpeg); it wasn't yet tested against the signed repository when the release notes were written. Since 0.8.8.6, the `lordos` package depends on `intel-microcode` and `amd64-microcode` on amd64, so the update installs the processor's microcode where it was missing (it loads at the next boot; without it the kernel kept the BIOS's, and on one i9-10900 reported MMIO Stale Data, SRBDS and GDS as vulnerable), and it recommends a common set of command-line tools (`curl`, `wget`, `rsync`, `jq` and others) from the same list the live ISO and the Raspberry Pi image read. Its per-user settings migrations remove keypad mappings imported from another terminal, an imported default profile that runs a command, and a Latin American keyboard saved as a default nobody chose. Since 0.8.8.7, Update All and the upgrade of one package also install the Recommends a new version adds, as apt's full upgrade does; before, the package engine followed only Depends on an upgrade, so tools newly recommended by the `lordos` package reached an installed system only through `apt`. A group is added only when none of its names were recommended by the installed version, so a recommended package the user removed stays removed, and one that can't be installed doesn't stop the update. The same version adds `whiptail` (61 KB, so debconf shows a package's questions as dialogs instead of failing back to plain text) and `zstd` (2.3 MB, the compressor Debian prefers for the initramfs) to both images and to the package's Recommends. 0.8.9 adds no root migration; three per-user settings migrations make the saved default wallpaper and accent mean "the theme's default" (5 and 7), so Lord Workspaces can have its own, and mark an account that already used LordOS so it never sees the first-start desktop chooser (6, §8). `lordos.service` now runs `lord-sessiond --release-cgroups` before it starts (§3.6), so a package upgrade or a restart with sessions alive works on systemd 258 and later.

## 3. The compositor

### 3.1 Displays without libdrm

`lord-server` sets display modes with the kernel's DRM ioctls directly (`kms.c`): it enumerates connectors, CRTCs and planes, allocates buffers, and page-flips on vertical blank. It picks the card that has connectors, not simply `card0`, which matters on boards where the display controller and the GPU are separate devices (on the Raspberry Pi 5, `vc4` and `v3d`).

### 3.2 Two ways to build a frame

- **CPU path.** The UI and app windows are copied into a canvas, and a "dumb" buffer is presented with a page flip. It needs nothing but the kernel. It is the default when there is no 3D-capable card, and `LORD_GPU=0` forces it (the boot menu's safe mode uses it). Since 0.8.5, heavy frames paint on a pool of up to 8 threads (`par.c`), only while painting takes more than 70 % of a frame at the target rate (since 0.8.6 also while the whole frame takes more than 60 %): the backdrop blur in phases and the row-local primitives split by bands of rows, with the same pixels as one thread (§7.2).
- **GPU path.** Mesa's GBM, EGL and GLES2 (`server/src/gpu/gpu.c`). The UI becomes one texture, and only the changed region is uploaded each frame (since 0.8.9, each damaged rectangle on its own, §7.2). App windows are not copied into the UI canvas: the UI leaves a transparent hole where each window goes, and window textures are drawn underneath, so an app that only changes its own content doesn't cause a UI repaint. Apps can hand over GPU buffers (`linux-dmabuf`) with no copies, and a fullscreen app with a suitable buffer is scanned out directly. The cursor uses the hardware cursor plane.

The path is chosen at start-up: a card without 3D (simpledrm, bochs, virtio-gpu without virgl, and others) uses the CPU without even loading Mesa; a software OpenGL renderer also falls back to the CPU, because composing with it costs more than LordOS's own CPU path. If a GPU frame fails, the GPU is turned off and the CPU path takes over.

**Status:** the GPU path runs on the Raspberry Pi 5's V3D and on VMware's virtual GPU (SVGA3D), was exercised with Mesa's software renderer in virtual machines, and composes on real hardware: the author's Radeon RX 580, used every day since November 2026, and, in community reports, Intel graphics on 14 machines (from Ironlake to Whiskey Lake, Cherry Trail and Gemini Lake) and three more AMD cards (a FirePro W6150M on the `radeon` driver, an RX 7800 XT and an RX 9060 XT) ([`docs/HARDWARE-REPORT.md`](https://github.com/lordbasex/LordOS/blob/main/docs/HARDWARE-REPORT.md)). Nvidia cards and AMD integrated graphics are untested.

### 3.3 Windows and input

- **Window management in C.** Moving and resizing run in C with one event per frame and no JavaScript, and a window being moved is drawn from its own layer. All four edges and corners resize, with LordOS's own cursors.
- **Input without libinput.** Keyboards, mice and tablets are read from evdev. Keyboard layouts come from `libxkbcommon` (every XKB layout, variants and compose).
- **Touchpad and touchscreen.** LordOS has its own multitouch driver (`server/src/tp`): pointer acceleration, tap and two-finger click, palm rejection, kinetic and natural scrolling, pinch, and three-finger swipes. Gestures reach both the LordOS interface and Linux apps (`zwp_pointer_gestures_v1`). It is tested with recorded gestures in `make test`. Since 0.8.8.6, Alps I2C touchpads whose driver sends a pressure above its declared range (044E:120B and others) tell a palm by the edges only, so one finger moves the pointer and taps click; any touchpad that reports more than its declared maximum stops using pressure for palms, and a new `tp-test` case built from that driver's report format covers it (issues #43, #54 and #67).
- **Keyboard shortcuts per theme (0.8.7).** One dispatcher (`sdk/shortcuts.js`) runs before every key listener, with a common base and a table per theme, so a key it takes reaches nobody else; that ended actions that fired twice in Lord Classic. Both themes get an app switcher with large app icons, most recently used first. Over a Linux app the desktop keeps only a fixed list per theme (`wl/keygrab.c`, `build/keygrab-test`): keyboard keys only, chosen by name, with no way to pass a key, and out of reach of isolated apps. In Lord Flow ❖ with C, V, X, A, Z, F, T, W, N, L, R, P or S reaches a Linux app as Ctrl, and as Ctrl+Shift in terminal emulators, to the focused client only. Settings → Keyboard lists the shortcuts of the theme in use, read only.
- **Pointer lock (0.8.7).** A lock or confinement now holds only with the pointer on the surface and the keyboard on its app, and ❖Esc always releases it (`wl/ptrlock.h`, `build/ptrlock-test`), so a window in the background can't hide the pointer as it passes over. This came from a report on a Raspberry Pi 5, reproduced there with a virtual mouse and keyboard: the Test Bench's plain L locked the pointer, and with no keyboard nothing let it go. Also ruled out on that board: a client killed while locked gives the cursor back at once, and a closed mouse path at 125 and 1000 Hz ends exactly where it began. The pointer speeding up by itself, which the report also described, was not reproduced.
- **Moving wallpapers (0.8.7; `docs/WALLPAPERS.md`).** Short loops behind the desktop and the login screen, downloaded on demand and checked against a SHA-256 in the signed package by a closed admin action. They need a compatible GPU, GPU composition plus hardware decoding of the file's format, and have no software mode. They pause when nobody sees them, with no input, on low battery and under load. The Raspberry Pi 5's HEVC decoder is driven through Raspberry Pi's FFmpeg. They can be a video of the user's own of up to 10 s, and the login screen can have a video or a still of its own. Each frame is still read back and copied on its way to the screen (measured in §7.4), and the Pi 5's decoder handles HEVC only, so H.264, VP9 and AV1 clips don't play there.
- **One wallpaper per display (0.8.9; every theme; `docs/WALLPAPERS.md`).** Settings → Wallpaper picks a display (all of them, or one by its model and connector) and then the picture, kept in `settings.wallpapers` by connector so three monitors of one model each keep theirs; the Control Center's quick pictures change the display it opened on. A picture for all displays clears the per-display ones. The same version adds **Cyberpunk City HD**, a category of seventeen pictures made for LordOS (two 3840×2160 originals with a 1920×1080 base, so a 1080p screen never decodes the 4K file; 22.4 MB with the thumbnails), and, in Lord Workspaces only, a slideshow per display (§8).
- **Window snapping and the pointer (0.8.9).** Dragging a window to a display's left or right edge fills that half of its work area, near a corner a quarter, to the top edge the whole area, now in Lord Flow too (Lord Classic and Lord Workspaces already did), and Settings → Desktop & Dock → Snap windows to the screen edges turns it off in every theme (#182). In Lord Workspaces the default arrow is LordOS's own rounded tip filled with the accent colour (`cursor_set_accent`, `lord.input.pointerAccent`, which takes only a colour; `build/cursor-test`), and Linux apps that ask for the default shape get it too; the other themes keep the black arrow.
- **Ending a session from the keyboard (0.8.9).** Ctrl+Alt+Backspace read Ctrl and Alt from a state kept across every keyboard, so a lost release (another console, a keyboard that slept) left them "held" and a lone Backspace ended the session with no trace in any log. The kernel is now asked whether Ctrl and Alt are really held on the keyboard that sent the Backspace (`EVIOCGKEY`), and `lord-server` logs why every session ends: the key and its keyboard, a signal with the sender's pid and uid, or the theme's Log Out.
- **On-screen keyboard (0.8.7; `docs/ON-SCREEN-KEYBOARD.md`).** For a computer with no physical keyboard. It opens only when asked for, from its button next to the clock, ❖⌃K or Settings, and from its button at the login and lock screens; it types in LordOS text fields, Linux apps, isolated apps and at the login and lock screens, follows the theme and the active XKB layout, and moves the window with the field out of its way. `lord.input.tap` takes one key from a closed list with no Ctrl, Alt, Super or function keys, so it can't be a shortcut, and only the theme and the login screen have it; a tap goes down the path of a physical key. An isolated app gets one broker call, a hint with a position and no text, obeyed only for the window in front. Nothing logs or keeps what is typed, and the panel is a protected node (§6.11). While it's open, a Linux app reports its field through `zwp_text_input_v3` so the field stays in view; X11 apps, and Chromium by default, don't. Tests: `build/osk-test`, `server/tests/osk_model_test.mjs`; run end to end on VM 125. On real hardware a person used it on a tablet PC (#127), where it can't type into the administrator password prompt, on purpose: that prompt takes only a physical keyboard (§6.11; [`docs/HARDWARE-REPORT.md`](https://github.com/lordbasex/LordOS/blob/main/docs/HARDWARE-REPORT.md)).
- **Shake to find the pointer (0.8.8.6).** A few quick left-right strokes with a mouse or a touchpad make the cursor grow for a moment toward 200 %, the largest the cursor plane takes, and shrink back half a second after they stop; on by default in Settings → Mouse & Trackpad. The detector (`server/src/shake.c`) is pure logic with its own test (`build/shake-test`, 12 checks: quick strokes grow it; short, slow, vertical or single long moves don't).
- **Keyboard lights and layout (0.8.8.6).** The Caps Lock, Num Lock and Scroll Lock lights follow the keyboard state: `lord-server` holds the keyboards exclusively, so it writes the lights (`EV_LED`) itself, also to keyboards plugged in later or handed back after a session switch. A user who never chose a layout types with the computer's own (`XKBLAYOUT` and `XKBVARIANT` in `/etc/default/keyboard`, or US without that file), never with the SDK's former Latin American default; the login screen falls back to US. Since 0.8.9.1 a session on a desktop computer starts with Num Lock on, so the keypad types digits (laptops keep it off: their keypad is often printed on the letter keys), and changing the layout keeps Caps Lock and Num Lock as they were.
- **Reading aloud from the keyboard (0.8.8.6).** ❖Esc reads what the window in front has selected and, pressed again, stops; ❖⇧Esc opens Live Speech (§5.1). For a Linux app it reads the app's primary selection, which the compositor keeps with the app that made it, reads only while that app has the keyboard and never hands to JavaScript (§6.7).
- **Keyboard focus and menus (0.8.8.8; `docs/DESIGN.md`, `docs/SHORTCUTS.md`).** Tab and Shift+Tab move between the controls of every LordOS app in tree order (`sdk/focus.js`, pure logic in `sdk/focusmodel.js`), skipping hidden and disabled ones and staying inside an open sheet or prompt. The focus ring works like `:focus-visible`: a 2 px line in the theme's new `focusRing` token, shown only after the keyboard is used and hidden by a press of the pointer. Space and Enter press, sliders, steppers and segmented controls take the arrows (swapped in right-to-left), scroll views scroll from the keyboard, and the Terminal, the Text Editor and a virtual machine's screen keep Tab. Menus in both themes and the right-click menus move with the arrows, Home and End and typed letters, open a submenu with → (← in right-to-left) and close one level at a time with Escape; F10, or the left ⌥ pressed and released alone, opens the menu bar, or Lord Classic's menu strip. Linux apps keep their own menus. Checked on VM 127 in Settings and with F10. Tests: `focus_model_test.mjs` (102 checks), `focus_scene_test.mjs` (41), `menu_nav_test.mjs` (68) and `menu_keys_test.mjs` (31).
- **Password fields (0.8.8.8).** Every LordOS password field, from the login and lock screen to Wi-Fi, Passwords, Databases and the Installer, is the SDK's `TextInput` with `secure`, which now has an eye that shows the text, hidden again when the field loses focus and on Enter, and a "Caps Lock is on" warning while it has focus. Shown, it is still a password field: no undo history, no input method, and Copy and Cut copy nothing. It adds no permission, broker message or `lord.*` call; isolated apps now start with the real Caps Lock state (`kb_set_locked`). Tests: `password_field_test.mjs` (32 checks) and `password_field_scene.mjs` (16).

### 3.4 Wayland compatibility

The compositor (`server/src/wl/wl.c`) uses only `libwayland-server` and code generated from the protocol XML. It offers: `wl_compositor`, `wl_subcompositor`, `wl_shm`, `wl_output` (one per display), `xdg_wm_base` with popups, `wl_seat` (pointer, keyboard, touch), `wl_data_device_manager` (a clipboard shared with LordOS), `zwp_primary_selection_device_manager_v1` (middle-click paste, 0.8.3), `zxdg_decoration_manager_v1`, the KDE server-decoration protocol (so GTK 3 apps such as Firefox get the theme's frame), `zxdg_output_manager_v1`, `wp_fractional_scale_v1`, `wp_viewporter`, `zwp_linux_dmabuf_v1` v4, `wp_presentation`, `zwp_relative_pointer_manager_v1`, `zwp_pointer_constraints_v1`, `zwp_pointer_gestures_v1`, `wp_cursor_shape_manager_v1` `zwp_idle_inhibit_manager_v1` (a video player keeps the screen on, 0.8.5) and, in 0.8.7, `zwp_text_input_manager_v3` (up to 0.8.8.7 only so the on-screen keyboard knows a field took focus and where its caret is; in 0.8.8.8, LordOS's input methods also compose through it, below). The compositor honors the frame an app asks for, also when it changes while the window is open (0.8.4).

**Checked from the outside.** The Test Bench (`lordos-testbench`, 0.8.5) is a plain Wayland client that binds each of these at the advertised version and exercises it: shm formats, outputs and their modes, xdg-output, fractional scale, a subsurface with a viewport, a popup, maximize and fullscreen states, the dmabuf feedback, clipboard and primary-selection round trips, idle-inhibit, cursor shape, relative pointer and gestures. Its first run found that the compositor didn't send a new selection back to the client that set it, as the protocol requires, and that idle-inhibit was missing; both were fixed the same day, and the run now gives 16 passed, 0 failed on VM 116 (`docs/PAPER-VALIDATION.md`).

Linux windows enter the SDK's window manager like any other, with title, focus, maximize, minimize and a Dock icon. Apps that ask for server-side decoration get the theme's frame; apps that draw their own (GTK 4) keep it, and their shadow is clipped. GTK 4 and libadwaita apps follow light/dark mode, the accent and the button order through an `org.freedesktop.portal.Settings` implementation that `lord-server` serves itself on the session bus; GTK 3 follows through the GSettings keyfile. From 0.8.8 to 0.8.8.7 the portal kept answering dark mode, a blue accent and the default buttons whatever LordOS was set to, because the file chooser's functions replaced the object that held `lord.portal.set`; this is fixed in 0.8.8.8.

**X11 apps (0.8.3).** When an X11-only app connects to the session's X socket, `lord-server` starts Debian's `/usr/bin/Xwayland` with a fixed command line, rootless, in its own scope and its own network namespace, with `no_new_privs`; the compositor is the X window manager (`server/src/wl/xwm.c`), so X11 windows get the same frame, Dock entry, per-app identity, firewall rules and restrictions as Wayland ones, and the clipboard works both ways. Isolated `.lpk` apps and Linux apps restricted from devices get no `DISPLAY`. Debian's `xwayland` package must be installed. Since 0.8.8.7 the session sets `GDK_BACKEND=wayland,x11` instead of `wayland`, so GTK apps still open on Wayland and GTK programs that only allow X11 open through Xwayland instead of failing at start. In 0.8.8.8 Qt gets the same fallback, `QT_QPA_PLATFORM=wayland;xcb` instead of `wayland`: a Qt app whose Wayland platform plugin is not installed (Debian's `qtwayland5` or `qt6-wayland`, which no Qt app depends on) opens through Xwayland instead of stopping at start (GitHub #96). Checked on VM 127 with MusicBrainz Picard (Qt 5) and Qt 5's Wayland plugins hidden: `wayland` alone aborted with "Could not find the Qt platform plugin", the list opened its window; with the plugins present Qt still chose Wayland. Also in 0.8.8.8, Xwayland requires the session's own random X cookie (`-auth`, an Xauthority file in the user's runtime folder, 0600): an X11 app run as root through `pkexec` or `sudo`, such as GParted, now opens its window instead of "cannot open display" (GitHub #107), while restricted Linux apps and isolated apps get neither the display nor the cookie.

**Linux apps in 0.8.8.8 (`docs/WAYLAND.md`, `docs/DESKTOP-PARITY.md`).** *Drag and drop:* `wl_data_device.start_drag` works between Linux apps, from Files to a Linux app and from a Linux app to Files, with offers, actions (copy, move, ask), the drag icon on the CPU and GPU paths, and a clean end when the source, the icon, the target or the client goes away mid-drag. A drag needs the serial of a current press of that client. A Files drag into a Linux app copies, and moves only with Shift held; a dropped `text/uri-list` is copied by Files into the folder under the pointer. A file list reaches LordOS only from a client that is positively unsandboxed (same root and mount, pid and user namespaces as `lord-server`, `wl/dndgate.c`), never from an isolated app or a Flatpak, and only while the interface handles the release that made the drop. Isolated LordOS apps take no drop; X11 windows do through the XDND bridge (below). Checked on VM 127: a file dragged from Files opened in Chromium, and a GTK 4 drop target got copy, or move with Shift held. *Files on the clipboard:* Copy in Files also offers `text/uri-list` and `x-special/gnome-copied-files` to Wayland and X11 apps; files copied in a Linux app paste in Files as a copy after a confirmation ("Paste N items copied in <app>?", Cancel by default), only from an unsandboxed Wayland client and only as this machine's `file://` paths (`wl/urilist.c`). *Input methods:* `zwp_text_input_v3` is complete, so LordOS's Korean, Japanese and Chinese input methods compose inside GTK 3, GTK 4 and Qt 6 apps, with the composition drawn by the app and the candidate window at its caret. Password, PIN, hidden and sensitive fields never compose, and what the app sends is cut to valid UTF-8 and to character boundaries (`wl/tiutf8.c`). GTK 4 doesn't choose that module by itself: 0.8.8.8 set `GTK_IM_MODULE=wayland` for the apps `lord-server` starts (checked on VM 127, a GTK 4 field got the Korean composition and then the finished text), but GTK 3 running on X11 inside Electron apps read it too and crashed (GitHub #150), so since 0.8.8.9 the variable is gone and LordOS's Settings portal serves `gtk-im-module` = `wayland`, which only GTK on Wayland reads (`ui/portal.c`; checked by `build/portal-gs-test`, not yet on a screen). *Primary selection:* LordOS's own text fields and the Terminal now take part, and a middle click pastes there too (Settings → Mouse & Trackpad → Middle click pastes turns it off). `lord.primary.get()` answers only while a middle-button press is being handled, and an app's `set_selection` needs an input serial it got in the last 10 s. *Activation and dialogs:* `xdg_activation_v1` lets a link opened from LordOS raise the browser already open, while a window that asks without a recent input of its own only gets an attention mark in the Dock or taskbar; `xdg-foreign-v2` and `xdg-dialog-v1` keep a Linux app's dialog, and the file chooser portal's, over its parent window and moving with it. *The session bus:* tray icons of Linux apps (StatusNotifierItem, with `lord-server` as watcher and host, `ui/sni.c`) show next to LordOS's status items with their menus, at most 32 items and 4 per connection; an icon named only as SVG is drawn by `lord-media` (below), and `IconThemePath` is not read. Checked on VM 127 with a GTK app using an indicator library. Media players that publish MPRIS (`hw/mpris.c`) appear in Control Center's Now Playing in both themes and get the media keys when LordOS's Player isn't playing; cover art is kept only from a local file. Checked on VM 127 with a video player: the tile showed its title and paused and resumed it, as did the play/pause key. Both use LordOS's own D-Bus client, with every call asynchronous, and no new library.

**More for Linux apps in 0.8.8.8 (`docs/WAYLAND.md`).** *Screen and window sharing:* `lord-server` serves `org.freedesktop.portal.ScreenCast` (version 4) itself, with no `xdg-desktop-portal`. `Start` shows LordOS's own chooser with the displays and the open windows, each with a live picture, under the name of the app asking. That name is only an identity LordOS verified (the app id of its launcher's scope); any other process is "An unknown program", with a warning. Nothing is shared until the person presses Share. While it runs, the screen-sharing indicator shows a pill with Stop, and a lock, a user switch, the window closing or the app leaving ends it. No `restore_token` is ever given, so the person picks every time. The frames are painted again in capture mode (protected windows are black) and go through a sealed memfd ring to `lord-screencast` (`server/src/cast/`), a sandboxed helper and the only binary that links PipeWire's client library. `lord-server` connects the user's PipeWire socket and hands it over; the helper applies its sandbox before it speaks, then lowers its own PipeWire permissions so it can create nothing, and the app's connection sees only the session's streams. An app with "no screen capture" is refused before any question, and the PipeWire guard hides every shared screen from it. Checked on VM 127 with a browser: 176 frames in 10 s at 1280×800, `lord-screencast` at about 2 % of a CPU, and nothing running when nothing is shared. Each buffer is its own sealed memfd, because a browser's capturer drops buffers that have no fd. *SVG icons:* tray and Dock icons that ship only as SVG are drawn by `lord-media` with vendored nanosvg, on an fd `lord-server` opened after checking the path (at most 1 MB). Elements and nesting are counted with a dry run of nanosvg's own tokenizer, shapes, points and numbers are bounded before rasterizing, and `lord-server` never parses SVG. Checked on VM 127 with the volume applet's symbolic icon, drawn in the bar's text color. *Apps that take the shortcuts:* `zwp_keyboard_shortcuts_inhibit_manager_v1` lets a virtual machine, a remote desktop or a game take ❖, ⌥Tab and the rest while it is in front, once the person allows it (the `shortcuts` permission, in Settings → Privacy). The decision goes by who `lord-server` checks the client is, never by the app_id it sets: `flatpak:<id>`, which also needs Flatpak's own record of the instance outside the sandbox, or `program:<resolved path>`, read through the socket's pidfd. Xwayland and isolated apps get none, and ❖Esc, the lock, the console switch and the media keys stay LordOS's. Checked on VM 127: the prompt shows the verified identity under the app's name. *Global shortcuts:* `org.freedesktop.portal.GlobalShortcuts` (version 1) gives an app the keys the person chooses in LordOS's sheet, with `Activated` on press and `Deactivated` on release for push-to-talk. It never gives a ❖ combination, a typing key or a key LordOS keeps; the choices are kept per app in a file `lord.fs` can't write and changed in Settings → Keyboard. *XDND:* the X window manager bridges drags both ways between X11 apps, Wayland apps and Files. An X app's files reach Files only when X-Resource ties the selection's owner to an unsandboxed process and no X client is sandboxed, and the data is read only from the X server's own `SelectionNotify`. *Security contexts:* `wp_security_context_manager_v1` lets Flatpak give each app a socket of its own; its clients count as sandboxed and don't see the trusted-only globals, and only an unsandboxed client may create one. *X11 apps on HiDPI:* X11 apps now scale themselves. Xwayland's pixels are device pixels on the densest display and `Xft.dpi` tells the apps the scale; Settings → Displays brings back the enlarged (blurry) way. *Terminal apps:* `Terminal=true` entries open in a Terminal tab (§1.2, §5.1). Global shortcuts, XDND, security contexts (no real Flatpak yet) and X11 HiDPI are built and covered by tests, but not yet checked on the VM.

**Linux apps in 0.8.9 (GitHub reports).** *Drag and drop (#176, #177):* the compositor counted the seat's held buttons and ended a drag only when the count reached zero, so one doubled press or one lost release kept every later Wayland drag going after the release; the held buttons are a set now and a drag also ends at the release of the button that started it, as Weston does (`wl/seatbtn.h`). A drag may also name a serial newer than its press and not newer than the newest the display gave out, as GTK 3 does after a click that focused the window, still only while that client's press is held on the window it names; Firefox's first tab drag in a window was refused before. Checked in `build/seatbtn-test` and `build/dnd-client`. *GTK 4 popovers (#159):* GTK 4 keeps one `wl_surface` for a popover and gives it new role objects each time it opens; the second opening got no configure and the app froze. A role object that goes now resets the surface's configure state (`role_reset`), checked by `tests/popup_headless.sh` against a headless `lord-server` in `make test` (before the fix 7 of 15 checks failed). *Full screen:* a fullscreen window now owns its own display only, so the pointer and the windows on the other displays keep working, and the keys follow the window chosen, not the pointer (#175, `wl/fsfocus.h`, `build/fsfocus-test`); without a GPU the CPU path paints a fullscreen window with its subsurfaces, scaled as one, as the GPU path did (Firefox in full screen showed the desktop; checked on the test VM with Firefox ESR and Chromium). A maximize or unmaximize request LordOS refuses is answered with the state as it is, which Google Chrome waited for. A move or resize request with no button down is ignored, as xdg-shell allows, so a window that draws its own title bar no longer follows the pointer after Minimize (#189). Dragging a window to the edges now snaps in Lord Flow too (§3.3).

**Shell extras (in development; latest release 0.8.9.4).** Five more protocols, approved by the maintainer on 2026-11-22, one file each (`server/src/wl/wlshell.h`; `docs/WAYLAND.md`, "Shell extras"). *Tab tear-off* (`xdg-toplevel-drag-v1`): a tab dragged out of a browser becomes a window that follows the pointer during the drag, is left out of the drag's hit test so it can be dropped back onto another window of the browser, and stays where it is let go; only a window of the app that owns the drag can follow. *Window tags* (`xdg-toplevel-tag-v1`): a window's tag keys its own remembered place, so each kind of window of an app reopens where that kind was. *The bell* (`xdg-system-bell-v1`): LordOS's alert sound, silent in Do Not Disturb, plus the attention mark for a window that isn't in front, at most one ring every 250 ms per app. *Session management* (`xdg-session-management-v1`): an app's windows come back at their place and size when it starts again; session ids are random and belong to the program `lord-server` checked the app runs, never to an id the app sent, so another app's id finds nothing; the file is written by `lord-server` only and protected from `lord.fs`. *Blur behind windows* (`ext-background-effect-v1`): drawn with the interface's own backdrop blur, and offered only where it can really be drawn, on the CPU path with transparency on; with GPU compositing the capability is none. Checked against a headless `lord-server` with a test client (`tests/shellx_headless.sh`, the tear-off with the pointer driven through the session's remote socket). Chromium 156 tore a tab off, kept it on the desktop as its own window and reattached it, on the same headless session; Firefox and the VM are still to try.

Still pending: explicit sync (in development since 0.8.9.4: `linux-drm-syncobj-v1` is built, `SYNCOBJ-PLAN.md`), single-pixel buffers, tearing control, content type and drawing tablets; drag and drop, LordOS input methods inside Linux apps (`text-input` v3), activation (`xdg-activation`), SVG icons and screen sharing for Linux apps, missing up to 0.8.8.7, arrived in 0.8.8.8. No screen-capture protocol is offered to apps: in 0.8.8.8 an app can only ask through the ScreenCast portal, and gets only what the person picks.

### 3.5 Several displays and HiDPI

Every connected display is driven at once, extended or mirrored, in one logical space, with an arrangement remembered by EDID identity and hotplug handling. Each display is painted at its own scale (100 to 200 % in 25 % steps; since 0.8.8.6, up to 300 %, as long as the desktop keeps at least 1024 × 600 logical pixels, so a 3840 × 2160 laptop panel at 300 % is a 1280 × 720 desktop; in 0.8.9, also 75 % and 80 % on displays whose desktop stays within 2560 × 1600 logical, for more space on small screens, with Wayland and X11 apps asked for 100 % and drawn smaller, not yet checked on the VM or a real 1280 × 800 laptop; #158), so text and vectors are rasterized at its real resolution. Linux apps get one `wl_output` per display and fractional scaling. Tested with two virtual heads (1280×800 and 2560×1600) on both paths. Real monitors on a PC appear in this paper only in 0.8.8.6's development, on one PC with a Radeon RX 580 and three monitors, where two fixes came from: the cursor plane is made at the size the driver asks for (128 × 128 there) instead of 64 × 64, which the driver scanned as 128 × 128, squashing the arrow; and the GPU path's framebuffers are removed only after the plain buffers are on screen, which ends the kernel's "atomic remove_fb failed" warnings inside a session. The same warning still came at every lock and logout, from the hand-off of the monitor between sessions, until 0.8.8.7 (§3.6). Since November 2026 that PC has been the author's daily LordOS machine, installed on bare metal. The community's machines ([`docs/HARDWARE-REPORT.md`](https://github.com/lordbasex/LordOS/blob/main/docs/HARDWARE-REPORT.md), by 2026-11-15: nine hardware reports with the report file and twelve more machines named in other GitHub issues, 22 physical machines with the author's PC) add 14 with Intel graphics, from Ironlake (2010) to Whiskey Lake (2019), Cherry Trail and Gemini Lake, and three more AMD cards: a FirePro W6150M on the older `radeon` driver, an RX 7800 XT on two 120 Hz monitors and an RX 9060 XT on one HDMI monitor. All of them reach the desktop; three laptops drive an external monitor, and a 15.3" 4K laptop panel runs at 300 %. DisplayPort hubs, Nvidia cards and AMD integrated graphics are untested.

Since 0.8.5, Settings → Displays numbers each display (the main one is 1) and **Identify** shows that number large on each monitor; dragging a display in the arrangement snaps it edge to edge and aligns it with the others, a drop never leaves two displays overlapping or apart, and the server keeps a position that fits exactly. A window can be sent to another display from the Window menu, and an app can be assigned to a display from its Dock item, kept by the connector name (HDMI-A-1, DP-2…) so two monitors of the same model are told apart (verified on VM 118). The sign-in and lock screen goes on the main display only, with the wallpaper on every display (since 0.8.9, drawn once per display instead of one picture over the whole desktop that showed a slice of it on each, #173), and follows displays plugged in or out (VM 118, two displays). Since 0.8.8.6 the login screen opens on the main display the user chose. It runs as its own system user without the user's `displays.json`, so it used to take the first connected connector (with three monitors and the first output dark, the password had to be typed blind). Now the session on the monitor tells `lord-sessiond` its main display's connector (only `[A-Za-z0-9-]`, up to 31 characters), which keeps it in `/var/lib/lordos/main-display` and passes it to the login screen, used when that connector is connected. The connector is used rather than the monitor's identity because identical monitors can report the same EDID serial.

**Figure: Lending the display to a session.**

```
[Login screen] Runs as lordos-greeter; only sends the request
    │ login request
    ▼
[lord-sessiond (root)] Verifies the password against /etc/shadow
    │ opens
    ▼
[Card and input] Opened as root, passed over a socket
    │ lent
    ▼
[User session] lord-server as the user, composing on GPU or CPU
    │ on a switch
    ▼
[Switch user] Input revoked, display control dropped, then lent to the next
```

*The visible session uses the GPU without ever being root; on a switch its access is revoked before the next session gets the devices.*

`lord-sessiond` is LordOS's own session manager:

- **The login screen** is a `lord-server` running as the unprivileged `lordos-greeter` user, with a special theme. It sends login requests to `lord-sessiond`; **passwords are always verified by the root process** against `/etc/shadow`, never by the greeter's JavaScript. Failed attempts are answered at a fixed 1.25 s, so timing reveals nothing. Since 0.8.5 it follows the kernel's display events, so a monitor plugged in after boot shows it, and it no longer stays running behind the user's session: it closes 10 seconds after a session takes the screen (about 53 MB of its own, 78 MB counting shared pages, measured in a VMware VM; the whole system went from 603 to 548 MB in use) and starts again in a few milliseconds on a lock, a user switch or a log-out. On a lock the screen goes dark first and only then is the login screen started, so the unlocked desktop is never left visible meanwhile.
- **The user's session bus first (0.8.5).** `lord-sessiond` starts `user@<uid>` and waits for the user's session bus socket (up to 5 s) before starting the session. With automatic login it used to start a few milliseconds too early, so the Secret Service of `lord-vault` and the notification server never got on the bus (§6.10).
- **One session per user**, all able to live at once (fast user switching). Each is a `lord-server` that starts as root and drops privileges right away.
- **Display lending.** `lord-sessiond` opens the graphics card and the input devices as root and lends them to the session that is on the monitor, over a Unix socket. On a switch it revokes them: `EVIOCREVOKE` makes the old session's input file descriptors stop working, and `DROP_MASTER` takes display control away, before anything is given to the next session. Since 0.8.5 access is still cut at once, but the devices are closed on a short-lived thread, because the last close of a USB mouse waits for its transfers to stop: from the lock to the sign-in screen went from 903 ms to 141 ms on a VMware Fusion VM, and a slow hand-off is logged with the time of each step. Until 0.8.8.7, `lord-sessiond` removed the leaving session's framebuffers while they were still on screen; amdgpu refuses to turn a plane off that way ("atomic remove_fb failed with -22" at every lock and logout), the displays went dark, and a DisplayPort monitor put to sleep like that might not wake until it was unplugged. Now every lit display first gets a black frame of its own mode, let go with `CLOSEFB`, which stays until the next session or the login screen shows its own, so nothing of the session stays visible and no link drops; logging out asks for the login screen at once, and the session closes its apps and unmounts its cloud folders off the screen. The visible session keeps composing on the GPU without ever being root. A session off the monitor draws in memory, and only if someone is watching it remotely.
- **Locking really takes the session off the monitor**; it is not a layer drawn on top. If the user's session hangs, the login screen still works. In 0.8.9 a login screen started for a lock applies the session's display-off and sleep deadlines as the notice arrives; before, a notice that came before its listener was dropped and the lock screen stayed lit and never slept (#172, `themes/greeter/inbox.js`).
- **Text consoles and text mode (0.8.9; `docs/SESSIONS.md`).** The keyboard is the session's, so the kernel never saw Ctrl+Alt+F1…F12. Now `lord-server` takes those keys and asks `lord-sessiond`, which keeps tty1 in `VT_PROCESS` mode and accepts only a console number from 1 to 12: leaving locks the session on the monitor (as Lock Screen) and takes the monitor back before the kernel switches; Ctrl+Alt+F1 brings tty1 back with the login screen locked for that user. For those who start the desktop by hand, as with `startx`: the boot menu gains **LordOS (text mode)** (`/etc/grub.d/11_lordos_text`, the system's first entry plus `lordos.text=1`), and Settings → Users → **Start in text mode** keeps it for every start through the closed admin action `boot-text` (§6.3). In text mode `lord-sessiond` leaves the monitor alone, `lordos-text-login.service` puts a login prompt on tty1, and `startlordos` there asks for the login screen over `/run/lordos/start.sock`, which exists only in text mode before the monitor is taken and accepts only someone logged in on the console in front, typing there (the caller read from the socket with `SO_PEERCRED`, its terminal from `/proc`, the console in front and that console's owner; `remote/startlogin.h`, `tests/startlogin_test.c`); the password is still asked on the login screen. Without `lord-sessiond`, `startlordos` runs `lord-server` as the user on that console, with no Lock Screen, administrator actions or per-app cgroups.
- **Restarts with sessions alive (0.8.9; GitHub #140).** On systemd 258 and later, `systemctl restart lordos` with sessions alive failed with "Device or resource busy" and left no login screen until a reboot: systemd 258 starts a delegated unit's new main process in the unit's root cgroup, which still had controllers on for the sessions. `lordos.service` now runs `lord-sessiond --release-cgroups` first: a control process with no input that notes the sessions' and scopes' limits in `/run/lordos/cgroup-limits` (root, 0600), turns the controllers off, and lets the new `lord-sessiond` turn them on and put every limit back; notes not yet put back are merged, never replaced (`sec/cgroup.c`, `build/cgroup-restart-test`). The scopes are unlimited for about a second during a restart. Debian 13 ships systemd 257, which wasn't affected; the unit hasn't been run on 258 or later yet.
- **Lock from logind (0.8.8.8; `docs/SESSIONS.md`).** `loginctl lock-session`, `loginctl lock-sessions` and an administrator's `LockSession` lock the desktop as ❖L does. The signal counts only from the connection that owns `org.freedesktop.login1` (`hw/logindlock.c`). In a logind session of its own, `LockedHint` follows the lock; `lord-sessiond`'s sessions are not logind sessions today, so a `Lock` of any session of the same user counts. logind's `Unlock` is never obeyed: only the password on the login screen gives the monitor back. Built and tested (`build/logindlock-test`), not yet checked on the VM.
- **Boot.** A LordOS GRUB theme draws the boot menu, and a LordOS Plymouth theme draws the splash (the crown with a progress bar). The hand-off has no black frame and no console text: Plymouth stops drawing and gives up display control while its last frame stays on screen, `lord-sessiond` takes display control and sets the first real frame of the login screen, and only then does Plymouth quit, keeping the splash on screen until it is replaced. Since 0.8.5 the splash shows the time since it started, About LordOS → Startup time shows how long this boot took from the kernel's start to the login screen (or the desktop, with automatic login), and every boot is logged with the LordOS version and build (`journalctl -b -u lordos | grep "first frame"`) and kept in `/var/lib/lordos/boot-times.jsonl` (the last 200 boots). In 0.8.9 a boot with no monitor connected no longer waits for the splash's timeout (a Raspberry Pi 5 used over SSH: 39.2 s → 8.6 s to `graphical.target`), and a session starts with the theme the person chose instead of loading the default one first and then switching (about 1.2 s less per login on the maintainer's PC).
- **Remembered places (0.8.7; `docs/WINDOWS.md`).** Each app reopens with its size, position, maximized state and display. A display is known by its monitor's name and connector, not its index; if it's gone or the place is off screen, the window opens in a visible area. Session restore comes first, a Dock assignment chooses the display, and dialogs and fixed sizes are respected. Tests: `tests/place_model_test.mjs`. Across two real displays it is not tested.
- **Session restore (0.8.7; `docs/SESSIONS.md`).** Apps open at logout, Restart or Shut Down come back with their frames, their maximized, minimized and snapped states, and their desktop; an empty desktop stays empty; after a power cut or a crash LordOS asks first. Settings → Session offers Always, Ask first and Off. What is saved in `settings.json` is typed Dock ids, never commands, titles or Linux document paths, and apps reopen only through the Dock's launch paths. Tested on VM 125 with a logout, reboots, a real shutdown, a forced power-off and `SIGKILL`. Browser tabs use the closed action `browser-restore on|off` (§6.3), fixed policy files for Chromium and Firefox ESR: pages came back on VM 125, and after a forced power-off Chromium needs its own "Restore pages?". The end of a session now asks Wayland and X11 apps to close, for up to 3 s, before disconnecting them, so browsers no longer record a crash at logout. It doesn't reopen a Files folder. In 0.8.9 the apps that hold a session or private data (Terminal, Passwords, Remote Desk, Machines, Databases, Camera, Recorder) reopen only when chosen, even with Always, and web apps come back with the session.
- **No usable display (0.8.7).** A card that opens but has no KMS, such as a render-only GPU, counts as no display: `lord-sessiond` stops trying to start the login screen on it, logs why and leaves a message on the text console, and the boot splash ends without keeping its picture over that message.
- **The login screen on the GPU (0.8.7; `docs/WALLPAPERS.md`).** `lordos-greeter` now joins `render` and `video`, so the login screen composes on the GPU instead of the CPU. That gives its process the GPU driver's attack surface; it already ran Mesa in software.

**Remote desktop.** The same service offers the desktop to a browser at `https://<address>:5673` (5673 spells "LORD" on a phone keypad). It is **off by default**, is turned on in Settings → Sharing, and accepts the local network only by default (0.8.3; a list of allowed networks or any address can be chosen, and LordOS's own VPN interfaces count as local). It uses TLS 1.2 or later with a self-signed P-256 certificate whose fingerprint Settings shows for comparison, a strict content security policy, same-origin checks and a session cookie that is `Secure`, `HttpOnly` and `SameSite=Strict`; the login page never lists user accounts. **Three failed sign-ins block the source address** for 15 minutes, then 1 hour, then 24 hours (IPv6 per /64), persisted by `lord-sessiond` alone, with manual block and allow lists; failures are answered at a fixed 1.25 s. Everything from the network goes through strict parsers with unit tests and a fuzz run under ASan and UBSan (0.8.3).

Since 0.8.4 the screen travels as **WebRTC video**: H.264 (VP8 when the browser lacks H.264) with the session's sound in Opus, encoded once per session by `lord-media` (VA-API on the graphics card when it can, x264 otherwise) for every viewer, with still areas made pixel-perfect by lossless tiles. Keyboard, mouse and clipboard go over a WebRTC data channel. Besides UDP, the video connects over TCP on port 5673 itself, so a firewall or VPN that lets only that port through is enough; the page reconnects by itself after an outage, and says why when it really can't connect. Since 0.8.8.7 `lord-media` decodes the graphics card's first H.264 keyframe with FFmpeg's software decoder before any packet goes out, and goes on with x264 from the current frame if it doesn't decode to a picture of the right size that looks like the frame that went in, if the card refuses a frame or if no packet comes for 8 frames; some drivers open the hardware encoder and then give a stream no browser can play (#94). STUN servers and a TURN relay (UDP, TCP or TLS) can be added for other networks. The process that serves a connection drops root as soon as it knows whose session it is and keeps only four descriptors. Since 0.8.5 the video follows the browser screen's refresh rate (60, 120, 144 Hz…) instead of a fixed 30, the bandwidth ramps up in seconds instead of minutes, and a top bar shows the frame rate, the encoder and whether the screen is composed on the GPU or the CPU (§7.2). Restart and Shut Down are offered only in the session on the monitor. Internet access is not intended; a VPN is recommended.

**Remote login (SSH).** Settings → Sharing also turns on Debian's OpenSSH server (0.8.1) through closed admin actions. Since 0.8.5 an **advanced, off-by-default option lets root log in over SSH**, with a public key only or with a key or a password, for tests and administration. Only administrators can change it, and every change carries the administrator's own password, checked as root against `/etc/shadow`. The modes write only fixed text to `/etc/ssh/sshd_config.d/05-lordos-root.conf` (read before the shipped `10-lordos.conf`, which keeps `PermitRootLogin no`), checked with `sshd -t`. The only user text written is one public key line validated in C (a known type, a blob that matches it, a printable comment, no options) into `/root/.ssh/authorized_keys`; keys are listed with their SHA-256 fingerprints, and root's password goes to `chpasswd` on standard input. A warning stays on the page while it is on. Tests: `build/ssh-root-test` (17 checks, the same fingerprints as `ssh-keygen -l`) and an end-to-end run as root on VM 116 (wrong password refused, a key added and accepted from another computer, a duplicate refused, the key removed, the mode off, `ssh root@` refused).

## 4. The UI engine

### 4.1 Not a browser

LordOS's interface is written in JavaScript with React, but there is no web engine underneath. WebKit or Chromium would cost 100 to 300 MB of RAM per process and would not be LordOS's code. Instead, the theme and the apps use a React renderer (`runtime/index.js`) that creates and updates **native nodes** in C: `View`, `Text`, `Image`, plus surfaces for Wayland windows and media. Styles are a subset of CSS (flexbox, colours, rounded and per-side borders, shadows, blur, transforms, transitions) applied by C code that the project controls. The model is close to how a mobile framework renders React to native views, except that the "native" side here is LordOS's own.

### 4.2 Pieces

- **JavaScript:** QuickJS 2025-04-26, a small ES2023 engine in C, vendored as source and embedded in `lord-server`.
- **React:** React 19.3.1 with `react-reconciler` 0.34, bundled with esbuild into each theme. The default theme with every app weighs about 1.9 MB (560 KB compressed) in 0.8.6.
- **Layout:** LordOS's own flexbox implementation (`layout.c`), with wrapping, logical start/end edges and right-to-left mirroring.
- **Painting:** LordOS's own 2D rasterizer with antialiased rounded rectangles, cached shadows, reduced-resolution blur and damage tracking: only the changed region is repainted. On ARM, optional NEON loops speed up blits and masks, verified bit-identical to the C code.
- **Text:** glyphs are rasterized with `stb_truetype`. Shaping is LordOS's own OpenType code (GSUB substitutions and GPOS positioning, colour emoji), with full Unicode bidi, Arabic joining, Indic shaping and the Universal Shaping Engine (409 of 409 test sentences identical to HarfBuzz in `tests/hb_compare.py`), CJK line breaking, Thai word breaking, and per-script font fallback. HarfBuzz, FreeType, fontconfig, fribidi and ICU are not linked by `lord-server`.
- **Input methods:** Korean (hangul), Japanese (kana and SKK) and Chinese (pinyin), in `server/src/ime.c`, with no ibus or fcitx; in 0.8.8.8 also inside Linux apps, through `zwp_text_input_v3` (§3.4).

**Figure: From a mouse move to a new frame.**

```
[evdev event] From the kernel
    │ read
    ▼
[Hit test] Which node is under the pointer
    │ JS event
    ▼
[React update] Only changed nodes are marked
    │ styles, children, text
    ▼
[Layout and paint] Only the damaged region
    │ back buffer
    ▼
[Page flip] On the next vblank, CPU or GPU path
```

*The engine repaints only what changed, then flips the page on the next vertical blank.*

### 4.3 How JavaScript reaches the system

The JavaScript side calls native services through `lord.*` APIs implemented in C (`server/src/ui/js_*.c`): `lord.fs` (files), `lord.settings`, `lord.net`, `lord.pkg`, `lord.media`, `lord.mail`, `lord.vault`, `lord.fw`, `lord.monitor`, `lord.fan` and others. Every call validates its arguments in C. The rules are strict:

- `lord-server` runs without root, and **no API executes arbitrary commands**.
- `lord.fs` writes only in the home folder and the user's own mounts, has no general "delete" (only moving to the Trash), and refuses the folders the system reads to launch or install something or that store security decisions: `~/.local/share/applications`, `~/.config/autostart`, the installed app folder, `settings.json`, the permissions file, the firewall rules, the blocklists, the mail accounts file and the vault folder. Since 0.8.5 its reading calls reach the whole system read-only as the user (Files → This Computer; the kernel's `/proc`, `/sys`, `/dev` and `/run` stay out, and the system's own permissions decide the rest); writing never widened, and isolated apps keep only their own data folder. In 0.8.7, `trash`, `rename` and a move of a folder that holds a protected path are refused too (`fs.protected`), and `rename` uses `RENAME_NOREPLACE`, so the kernel refuses an existing target with no gap after a check.
- Anything that needs root goes through `admin.c`: a closed table of actions with arguments validated on the root side, fixed program paths and configuration generated by LordOS, never user text passed to a shell. Passwords go through standard input, never on a command line.
- Long work never blocks a frame: helpers and services are polled from the main loop without waiting.
- Calls that reach the network for the desktop exist only in the desktop's own context, never in an isolated app: in 0.8.9 `lord.weather` and `lord.media.stream` and `m3u` (§6.7). A desk widget's data comes from one shared feed (`sdk/widgetfeed.js`) that reads each value once however many widgets show it and not at all while none can be seen (behind a window, the displays off, the session locked).

### 4.4 Languages

The interface ships in English (the default), Spanish, Portuguese, French (0.8.8, a first translation with no native review yet), Italian (0.8.8.2) and Lithuanian (partly in 0.8.8.6; complete since 0.8.8.7, every app and message, all 11,909 keys, with Lithuanian plurals and the emoji and country names from CLDR 45), and more languages are added as language packs without code changes. Since 0.8.8.9, 29 more languages ship, complete too, chosen from lordos.org's own visit statistics (every language of a country with at least 5 distinct visitors in 30 days): Indonesian, Japanese, German, Hindi, Malay, Bengali, Simplified and Traditional Chinese, Ukrainian, Polish, Arabic, Vietnamese, Swedish, Greek, Dutch, Turkish, Hungarian, Persian, Russian, Romanian, Finnish, Urdu, Bulgarian, Korean, Thai and Azerbaijani; and, chosen the same way on 2026-11-15, Catalan (Spain), Filipino (the Philippines) and Swahili (Kenya). In 0.8.8.8, text fields place the caret and the selection from the shaped, reordered text (`lord.text.carets`, `ui/caret.c`): Hebrew or Arabic mixed with numbers gets one selection rectangle per piece on screen, and ← → move on screen. The arrows, Backspace and Delete move by grapheme cluster (UAX #29, `ui/grapheme.c`), never inside an emoji sequence, a flag or a letter with its marks; `build/bidi-test` runs Unicode's 1,187 `GraphemeBreakTest.txt` cases. Not yet checked on the VM.

### 5.1 Native apps

Thirty-five native apps ship with LordOS (Cleaner and Remote Desk joined in 0.8.7, Machines in 0.8.8.5, Databases in 0.8.8.7, §10.1), all React apps on the same engine and SDK: Files, Settings, Terminal, Store, Text Editor, Notes, Calculator, Monitor, PDF Viewer, Fonts, Emoji & Symbols, Scanner, Photos, Player, Screenshots, Camera, Recorder, Passwords, Disks, Backups, Logs, Clock, Help, Mail, Calendar, Contacts, Reminders, LordOS Imager (0.8.4), System Information (0.8.5), Cleaner and Remote Desk (0.8.7), Machines (0.8.8.5), Databases (0.8.8.7), About and the installer. Since 0.8.8.7 a release package is refused when an app changed and its version didn't (`tools/app-versions.mjs`), after 0.8.8.6 shipped changed apps with their old versions (#91). Some highlights:

- **Desk widgets (0.8.9; every theme; `docs/WORKSPACES.md`, "Widget data").** "Add widget…" in the wallpaper's right-click menu opens a catalog with search and categories (Time, System, Devices, Network, Productivity, Media; `sdk/widgetpicker.jsx`), and each widget takes a block of its display's grid: Clock (analog, analog with a second hand in the accent colour, or digital, and world cities), Calendar, Weather, System, Network, Disks, Temperatures, Battery, Devices, VPN, Timer, Recent files, Updates, Apps, Reminders, Clipboard, Video, Sound wave, Claude Code, Now playing and Read aloud. ### 5.2 Installable `.lpk` apps

Third-party native apps are packaged as `.lpk`: a gzip-compressed tar with a manifest, the bundled `app.js`, a required icon, optional translations and assets. An app doesn't carry React or the SDK; it uses the system's, which keeps it small (the example Fractal app weighs 5 KB). They install without root into `~/.local/share/lordos/apps/<id>/`. The installer rejects links, devices, absolute paths, `..`, odd characters, more than 2,000 files or 64 MB, and replaces the previous version atomically. Each one runs isolated (§6.4).

### 5.3 The Store and Debian packages

The Store (redesigned in 0.8.5) has a sidebar in three groups (Discover, For this computer, Installed and Updates; Artificial Intelligence and Debian's ten categories with their counts; LordOS apps) and shows apps as cards in a grid that fills the window: icon, name, category, two lines of summary, the download size and a Get, Open or View button. Discover opens with a featured banner, then the AI shelf and a shelf per category; an app's page has a row of facts (version, size, category, distribution). It shows Debian's apps by category with search, `.lpk` apps and local `.deb` files, suggestions for this computer's hardware (missing firmware, printer and scanner drivers, guest tools, 0.8.2; their own page, For this computer, since 0.8.5), and LordOS's own updates (0.8.1), and always shows a plan before installing or removing. Debian packages are handled by **LordOS's own package engine** (`server/src/pkg`): it reads the apt sources, verifies `InRelease` signatures with its own OpenPGP code (RSA and Ed25519), refuses expired, replayed, wrong-suite or trailing-data indexes, checks every index and `.deb` against SHA-256 values from the signed index, and resolves dependencies (plans identical to apt's in 12 test cases). Only the last step is Debian's: `dpkg` unpacks and configures, and remains the only writer of its database, so `apt` keeps working. Since 0.8.5, `https://` sources are fetched over HTTPS through `lord-tls`, a sandboxed helper that checks the certificate chain and the host name and only relays bytes (§6); before, they were fetched over `http://`. Integrity still rests on the signatures and hashes either way; HTTPS adds privacy (the package names downloaded are no longer visible on the network) and refuses a server that isn't who it claims, and a secure download is never redirected to plain HTTP. `lord-tls` is executed by the download child (running as `nobody` in its own download scope) with a fixed path, no arguments, an empty environment and the already-connected socket; it applies the helpers' sandbox before it reads anything, uses TLS 1.2 or later with SNI, never parses HTTP and never decides about packages. The Store's update and installs used it on VM 116 and on a VMware machine. Since 0.8.5 the engine also sends a `+` in a package name as `%2B`, as apt does, so packages such as `kms++-utils` download from lordos.org's CDN.

In development after 0.8.9.4, the Store's sidebar is arranged by where apps come from: Linux apps from Debian, Flathub, Web apps and LordOS apps (Wine and Android said as coming soon), and Picked by LordOS (Artificial Intelligence, Commercial, Remote access, Third-party apps); each origin opens with its categories and how many apps each has. Browsing no longer freezes the pointer: the package index's answers are kept until the index or the language changes, and a category shows 60 cards at a time.

### 5.4 Linux apps

Linux apps with a `.desktop` file appear in the app launcher. Launching goes through `lord.apps.launch(id)`: the interface can only name an installed `.desktop` file; `lord-server` re-reads it, checks it, builds `argv` from its `Exec` line by the specification and runs it with `execve`, without a shell or caller arguments, inside its own root-owned cgroup scope. Chromium and Firefox are preinstalled in the ISO and the Raspberry Pi image; since 0.8.4 they draw a single bar with their tabs and LordOS's window buttons (one switch in Settings → Appearance brings back the LordOS frame), and an optional extension keeps video smooth without hardware decoding (0.8.2). X11-only apps run through Xwayland (§3.4). **Linux apps are not sandboxed by default**: they run as the user, as on any Debian system. They get attribution, the per-app firewall and the per-app restrictions the owner sets (§6.6), including an optional "no access to your files" view applied by the launcher. Since 0.8.5 a `.desktop` file whose name has a space or another unusual character (the LordOS Imager's is `LordOS Imager.desktop`) gets an id with those characters turned into `-` and is launched from its real file, and **Force Quit…** (Lord Flow's crown menu) ends a Linux or isolated app's own process only, through `lord.wayland.kill`, which accepts only a Wayland client of the same user (an X11 app is asked to close instead). In 0.8.8.8 they also exchange drags and copied files with Files, type with LordOS's input methods, show their tray icons next to the clock and play in Now Playing (§3.4). They can also share a screen or a window, take the shortcuts while in front, use global shortcuts and drag with X11 apps (§3.4).

**Web apps (0.8.8.8; `docs/WEBAPPS.md`).** The LordOS Web Runtime installs web apps and PWAs as LordOS apps. `lord-web` (`server/src/web/`) runs one process per app and profile and is the only binary that links WPE WebKit (Debian 13's `libwpewebkit-2.0` 2.48). It ships in the optional package `lordos-web`; without it the rest of LordOS works unchanged. WebKit's own sandbox (bubblewrap, seccomp, `xdg-dbus-proxy`) runs its web and network processes and is never turned off. Only `lord-server` starts `lord-web`, from the fixed path next to it and with exactly `--app <app> --profile <profile>` (plus `--inspect` for developer tools, below). The registry (`~/.config/lordos/web/`) and each profile's data are in folders `lord.fs` can't write. Each app has its own window and Dock icon, its profiles (separate accounts, each with its own cookies), its own firewall scope (`lordos-web-<app>`) and a cgroup with memory and CPU limits. The Store's Web apps section lists a catalog that ships with LordOS and adds a site from its address: `lord-web --probe` reads its manifest and icon in a throwaway session, never following `https` to `http` or a public address to a local network, and nothing is installed until the person confirms. Notifications, camera, microphone, screen and location are asked once per app and kept in Settings → Web Apps. They are answered only for the `lord-web` that `lord-server` started for that app and profile, and only for the app's own pages. A page's copies to the clipboard reach `lord-web` only through a script in an isolated world that the page's scripts can't see, injected only into the app's own top-level documents, and `lord-web` checks the address again for each one. A drag from an isolated LordOS app or a Flatpak reaches a web app as text only, never as files, and a dropped file is opened without following a link anywhere on its path. In background mode, closing the window keeps the app running behind its tray icon. A probe peaked at 224 MB PSS on the main machine. `lord-web` now runs on VM 127; before that, only the engine was tried there, with WPE's reference browser loading a messaging web app (about 810 MB PSS for one account). Web apps follow the desktop's light or dark mode: WPE 2.48 has no API for a page's `prefers-color-scheme`, so a script of `lord-web`'s, with no privileges, makes the page's `matchMedia` answer with the desktop's mode and sends `change` when it flips, live (checked on VM 127); `lord-server` tells `lord-web` the mode with one closed word, `light` or `dark`, and only from its own process. Pages that choose their colors only through CSS media queries stay light until a newer WebKit. In 0.8.8.9 a per-app Appearance (Light or Dark instead of the desktop's mode) is built but held back until `lord-web` moves to the new WPE API, WPEPlatform (GitHub #142, before 1.0), because WPE 2.48 can't set the scheme for CSS and the choice only half worked: for now every web app follows LordOS's mode, Settings shows Automatic with Light and Dark unavailable, and `lord-server` reads a stored Light or Dark as Automatic. A site with a theme setting of its own (WhatsApp, for example) keeps it. Also since 0.8.8.9: each profile's *Browser identity*, the browser its pages are told it is, from a closed list of four Linux browsers (Chrome on Linux, sent exactly as Chrome sends it, the new default; Edge on Linux; Firefox on Linux; or LordOS's own WebKit string, the one every app had before; a fifth, LordOS alone, was removed after a messaging web app refused it, as it refused Chrome's string with LordOS's token added); `lord-web` maps the word to the string in C, the page never names one, and a change reaches a running profile through one more closed call from `lord-server` only, then the page loads again. LordOS still renders with WebKit whatever the string says. Also since 0.8.8.9: a web app opened without network shows LordOS's own "No connection" page (with no script, in the person's language and the desktop's colors) and loads its address again by itself after 2, 4, 8, 16 and 32 s and then every minute, at once when the network comes back, and on Ctrl+R (GitHub #144); not yet checked on screen. Also since 0.8.8.9: *Developer mode* (Settings → Web Apps, one switch, off by default) adds *Inspect (developer tools)* to a web app window's Window menu. After the person confirms a question that says the tools see everything in the app, `lord-server` starts that app and profile's `lord-web` again with `--inspect`, which `lord-web` accepts only while the switch (in the folder `lord.fs` can't write) is on: WPE 2.48 turns its remote inspector on only as the process starts, from `WEBKIT_INSPECTOR_HTTP_SERVER`. `lord-web` hands it `127.0.0.1` and a port on the browsers' "bad port" list, which no web page can reach, checks that the listening socket on it is its own, and opens WebKit's Web Inspector in the person's browser through a gate of its own on another port: a one-time address (256 random bits, handed only to the browser, never shown in the notification) sets an HttpOnly, SameSite=Strict cookie, and every later request, the inspector's WebSocket too, must carry it with the gate's own `Host` and `Origin`, so another site's page, a page on another port and DNS rebinding are refused. It ends with the window. WebKit's own ports still have no token, so while it is on any process on the computer can connect to them directly, which is why it is per window and asked every time. No D-Bus method was added and the page can't turn it on. Checked against a headless `lord-server` (the page listed, the inspector's WebSocket answering, nothing listening without `--inspect`) and, for the gate, with headless Chromium (the inspector working through it; foreign, rebinding and malformed requests refused), not yet on screen. The catalog has 37 apps, each starting at the service's own address; only one chat app is marked tested on LordOS (two accounts), the rest say not tested yet. Discover shows them with a banner and a shelf, and installing the first one also installs `lordos-web` with no other click (checked on VM 127, up to the app's own window with its Dock and tray icons). A web app's window has Undo, Redo, Cut, Copy, Paste and Select All in its Edit menu and LordOS's own right-click menu, both from closed lists checked on both sides; an unread count on its Dock icon, a notification sound per app and a color per profile; and a hidden window's page stops painting and runs its timers at most once a second (a busy page went from 115 % of a CPU to 0.4 % while minimized, on the development VM).

**What the LordOS Web Runtime is.** A native web application runtime written in C, built on WPE WebKit, that installs and runs web apps and PWAs as LordOS apps, without an external browser. It is not a native client of any service: the page is the site's own web interface. LordOS doesn't change the sites or their PWAs; it runs them as their sites serve them, and adds only the window, the desktop integration and the security around it. Where WPE 2.48 lacks something a desktop needs (the Async Clipboard API, drag and drop, selecting by dragging, the Edit and right-click menus, the color scheme), `lord-web` adds small documented scripts of its own (`docs/WEBAPPS.md`), and those that talk to `lord-web` do so only from an isolated world the page can't see, without changing the site's code or content.

| | Plain web wrapper (a site in a desktop window) | PWA installed from a browser | LordOS Web Runtime |
|---|---|---|---|
| Runs the page | A web view in a window | That browser's engine and profile | Its own `lord-web` process per app and profile, on Debian's WPE WebKit |
| Engine sandbox | Depends on the wrapper | That browser's | WebKit's (bubblewrap, seccomp), never off |
| Permissions, firewall, limits | Depends on the wrapper | Kept by the browser | Asked once per app; the app's own firewall scope and memory and CPU limits |
| Desktop integration | A window | Varies | Dock icon and badge, notifications with the app's sound, menu bar, Edit and right-click menus, tray, light and dark |

The first two columns describe those kinds of apps in general, not any product.

### 5.5 WebAssembly

LordOS includes its own WebAssembly interpreter in C (`server/src/wasm`), exposed as the standard `WebAssembly` global, so a native app can carry modules compiled from C, C++, Rust or Zig. It covers WebAssembly 2.0 without SIMD (the MVP plus sign extension, saturating conversions, multi-value, bulk memory and reference types), passes 26,290 of 26,290 assertions of the official test suite on the VM, and turns every error into a trap rather than a crash. On the project's example it ran 3 to 5 times faster than the same code in JavaScript.

### 5.6 Installing LordOS

- **Live ISO** for 64-bit PCs, with a graphical installer (UEFI and BIOS). In 0.8.8 the installer can also install in free space: on a GPT disk with an EFI partition, booted through UEFI, it adds LordOS beside what is there as one new partition and leaves every existing partition as it was. The wizard, the disk checks and the rollback were tested, and the whole install ran to the end in a virtual machine (#7): LordOS booted from the disk and the account logged in, with the existing partitions unchanged; the other system there was a test file, so starting a real second system beside it has not been tried (§10.2). A community laptop runs LordOS installed next to another system (#129, [`docs/HARDWARE-REPORT.md`](https://github.com/lordbasex/LordOS/blob/main/docs/HARDWARE-REPORT.md)).
- **OVA for virtual machines** (0.8.8): `lordos-<version>-amd64.ova` opens in VirtualBox or VMware. It starts with 4 CPUs and 4 GB of memory, the minimum for a virtual machine; 16 GB is the ideal with many apps. The first account is made in the installer's screens on its first boot; until then it starts in a setup session whose administrator account has no password, reachable only at the machine's own console. Tested in VirtualBox (the account is made and the system restarts into the login screen) and, with the same steps, in VMware Fusion; not tried in VMware Workstation.
- **Live ISO for arm64** (0.8.7): `lordos-live-<version>-arm64.iso` for generic UEFI arm64 machines and virtual machines, with the live desktop and the disk installer; the Imager lists it as "Generic arm64 (USB stick)". - **Raspberry Pi 5 image** for SD card or NVMe (§7.4), written and prepared with the LordOS Imager, which also writes a first-run file the board applies once at its first boot (strictly validated; nothing is applied if any part is wrong).
- **On an existing Debian 13**: `curl -fsSL https://lordos.org/install.sh | sh`. The script asks before changing anything, downloads `SHA256SUMS` and verifies its Ed25519 signature with the release key embedded in the script, refuses to continue without a valid signature, checks the `.deb`'s SHA-256, installs it with apt and sets the system up like the ISO. The release files are published on GitHub Releases. In 0.8.7, a Debian with a root password no longer ends up with nobody as an administrator: the script picks the user who logged in, or the only regular user, offers to make that user an administrator and installs `sudo`, and a system already in that state can get out of it from the Store with the root password (§6.3). Tested on a clean amd64 Debian 13 virtual machine with a root password, one regular user and no `sudo`; logging in on the login screen was not part of that run. On real hardware, one community laptop runs LordOS installed this way over its Debian 13, an HP ZBook 17 G2 (#40, [`docs/HARDWARE-REPORT.md`](https://github.com/lordbasex/LordOS/blob/main/docs/HARDWARE-REPORT.md)).

## 6. Security

### 6.1 Threat model

LordOS is designed against these threats:

- **A malicious or compromised installed app** that wants the user's files, keys, microphone, camera, clipboard or network.
- **Malicious documents and messages**: PDFs, archives, fonts, images, video and mail crafted to exploit a parser.
- **A Linux app that wants to send data out**, or to escape the rules set for it.
- **An attacker on the local network** trying to use the remote desktop or to tamper with downloads.
- **A malicious or impersonated server** that the user connects to over SMB, NFS, SFTP, FTP, WebDAV, RDP or VNC, or that answers on the local network.
- **Tampered packages and releases.**

Outside the model, for now: a compromised kernel or root account; physical attacks; side channels; and Linux apps that the owner hasn't restricted, which run as the user, as on any Debian system, and can read the user's files. Linux apps are confined only by the restrictions the owner sets for them (§6.6), and only when they are started from the app launcher.

### 6.2 Least privilege

- `lord-server` runs as the user. In a managed session it never holds the display or input devices itself: `lord-sessiond` lends them and revokes them.
- Libraries that parse untrusted data are linked only by helpers: FFmpeg, libva and the video encoders by `lord-media` (and FFmpeg, in 0.8.9, also by `lord-stream`, the same player built with network, §6.7); Poppler and libarchive by `lord-doc`; OpenSSL by `lord-maild`, `lord-fetch`, `lord-tls` (HTTPS for the package engine's downloads: it verifies the certificate and the host name and only relays bytes; the signed index still decides about packages) and `lord-sessiond`; libsrtp2 and usrsctp by `lord-sessiond`, used only in the bridge that runs as the user after sign-in; Monocypher by `lord-vault`; libfreerdp by `lord-rdesk`. Since 0.8.8.7 `lord-sql` also links OpenSSL, for the TLS that starts inside the MySQL handshake.
- Helpers receive files and devices as file descriptors opened by `lord-server`; they never open paths. Two exceptions in 0.8.7, both before the sandbox closes: `lord-media` opens the Pi 5's two decoder devices for one job, and `lord-rdesk` opens the folders chosen for sharing over RDP (§6.7). In 0.8.9 a third: `lord-hidpp` opens the hidraw nodes of Logitech devices it finds in sysfs, while it still holds its group, then drops the group and takes the sandbox before it speaks to them; `lord-stream` gets a network address, never a path.
- The compositor never waits for a helper or an app, so a crash or a hang stays contained.

### 6.3 The root processes and their closed interfaces

| Process | Accepts | Never does |
|---|---|---|
| `admin.c` helper | a fixed table of actions, arguments validated as root | generic actions, user text in a shell |
| `lord-sessiond` | login requests from the greeter; short session JSON (≤ 4 KB); a session's console switch, only a number from 1 to 12 (0.8.9); in text mode, a request for the login screen on `/run/lordos/start.sock` from the person logged in on the console in front, typing there (0.8.9) | let the greeter verify passwords; read pixels as root; read anything but the caller from a `start.sock` request |
| its cgroup placement child | `enter <scope> <limits>` for the calling process only, from a session's `server` leaf, running a binary from `lord-server`'s directory | place arbitrary processes; hand the tree back to the user |
| `lord-sessiond --release-cgroups` (0.8.9) | nothing: `lordos.service`'s first `ExecStartPre`, with no argument besides the mode | take a path, a pid or a value from anywhere but its root-only notes file and the service's own cgroup subtree |
| `lordos-lid-wake` (0.8.9) | `pre`\|`post` and one of four kinds of sleep, from systemd-sleep | run anything; write anything but a `LID*` name read from `/proc/acpi/wakeup` back to it, and its own note; act on a desktop or with a lid closed |
| `lord-netd` | `net-*` actions from root peers only | non-network actions; run anything from a session |
| `lord-netperm` | `RELOAD` with no data | run programs; take arguments; open internet sockets |
| `lord-fand` | `STATUS` for anyone; `PROFILE`, `CURVE`, `FORCE` for administrators | name paths or devices; run programs; use the network |
| the Store's download child | moves its own pid into its root-owned download scope, from its session's `server` leaf, then drops to `nobody` | place any other process |

The admin helper's table gained, in 0.8.5, only closed actions of the same kind: `pkg-source-add` and `pkg-source-remove <id>` (§5.3: only a catalog id from the interface; the entry, its key's fingerprint and every field are checked as root against the root-owned catalog the lordos package ships), `ssh-root`, `ssh-root-key`, `ssh-root-password` and the read-only `ssh-root-status` (§3.6: administrators only, each change with the administrator's own password checked as root), and the read-only `hw-memory-modules` (System Information: SMBIOS memory devices parsed strictly in C, never serial numbers, asset tags or part numbers).

In 0.8.8 the table also gains `wallpaper-image` and `wallpaper-login-image`, for a person's own picture, `install-account`, for the OVA's first account, and `keyboard-light`. In 0.8.7, the table gains more closed actions of the same kind: `clean-status`, `clean-journal`, `clean-apt-cache` and `clean-var-tmp` (Cleaner, no arguments); `share-mount` and `share-unmount` (Files → Network, §5.1: every field validated as root, private IPv4 addresses only, one `fsconfig()` call per option with no program or shell, the password wiped after its one call, only under `/media/<user>`); `browser-restore on|off` (session restore, fixed policy files); the read-only `rpi-pmic` (the Monitor's Voltage view, Raspberry Pi 5 boards only: the fixed `vcgencmd pmic_read_adc`, parsed strictly in C, with a closed list of rail names); `rpi-case-detect` (administrators, no arguments: makes the USB-C controller a host until the next restart and looks for the Argon ONE V5 case's two chips; nothing is written to the boot partition); the read-only `hw-serial-numbers` (administrators, no arguments, validated in C, answered only to the request that asked); and `admin-rescue` with the read-only `admin-rescue-status`, open to non-administrators because they are the only ones who need them: each decides again as root, refuses when any administrator exists, when root is locked or has no password, or when `sudo` is missing, and runs only `/usr/sbin/usermod --append --groups sudo <session user>` (`wheel` on a system with no `sudo` group; who counts as an administrator is one fixed list, `sudo`, `admin` and `wheel`, in `server/src/users/admingroups.c`, shared by every administrator check since 0.8.8.9). Moving wallpapers add three more: `wallpaper-get` (anyone), `wallpaper-remove` and `wallpaper-login` (administrators). Since 0.8.8.9, with no new action: `disk-mount` and `disk-unmount` also accept a free partition of the system disk, for administrators only, decided as root from the kernel and udev, and every NTFS volume left hibernated is mounted read-only (§5.1); and `power-buttons` takes an optional fourth value from the same short list, the action for a 5-second hold (logind's `HandlePowerKeyLongPress`), so a tablet sleeps on a tap and shuts down on a hold, its new default on new installs and, through migration 008, where nobody chose otherwise. JavaScript names a catalog entry, never a URL or a path; the file comes only from the project's own repository on GitHub, through a child running as `nobody` in the Store's scope, and a file whose size or SHA-256 isn't the signed catalog's is deleted. `disk-mount` now checks the Disk Formats item and always mounts HFS+ read-only.

**In 0.8.9** the table gains three closed actions, each approved by the maintainer on 2026-11-17 and each for administrators only: `battery-thresholds <start> <end>` (the kernel's `charge_control_start_threshold` and `charge_control_end_threshold`, integers from 50 to 100 with the start below the end, checked as root) and `battery-behaviour <mode>` (`charge_behaviour`: only `auto`, `inhibit-charge` or `force-discharge`, and only one the battery lists), both written to a system battery that root chooses itself under `/sys/class/power_supply` (type Battery, not a device's), never a path or another value from the caller (`hw/battery_admin.c`); and `boot-text on|off` (Settings → Users → Start in text mode), which only writes the fixed file `/etc/lordos/text-mode` from fixed text or removes it, a file `lord-sessiond` reads only when it is root's and not writable by others (§3.6). Two more root pieces come with the package, neither reachable from `lord-server` or JavaScript: `lordos-lid-wake` (`hw/lidwake_tool.c`; GitHub #172), a systemd-sleep hook that links libc only, executes nothing, reads only kernel files at fixed paths parsed strictly (`hw/lidwake.h`), acts only on a portable chassis (SMBIOS types 8, 9, 10, 14, 31 and 32, `hw/chassis.h`) with every lid open and only on enabled `LID*` wake devices, notes them in `/run/lordos/lid-wake` (root, 0600) and turns back on after waking only what it noted and is still off; and `lord-sessiond --release-cgroups` (§3.6). `lord-hidpp`, the only setgid binary of LordOS, is in §6.7.

**In development after 0.8.9.4** two closed actions for Machines' bridged network, approved by the maintainer on 2026-11-20: `vm-net-bridge` (administrators: a machine id, a card name and a MAC, each checked as root; the card must be a physical wired Ethernet card, never Wi-Fi, a bridge, a bond or a virtual card) makes one macvtap in bridge mode with that MAC and nothing else (no address, route, forwarding or firewall rule) and hands its `/dev/tapN` to the person, mode 0600; `vm-net-unbridge` removes only the caller's own unused one, and a sweep removes leftovers when a session starts and ends (`server/src/vm/vmnet_admin.c`). QEMU gets only the descriptor. A bridged machine's frames aren't sockets, so LordOS's firewall doesn't see them; Configure says so.

### 6.4 What is isolated, and the app sandbox

Not every program on LordOS is sandboxed. This is exactly what applies to each kind:

| Kind | Process | Sandbox | cgroup scope | Broker and permissions | Firewall and restrictions (§6.6) |
|---|---|---|---|---|---|
| `.lpk` apps, and Passwords, Mail, Calendar, Contacts and Reminders (0.8.2) | own (`lord-server --app <id>`) | Landlock, seccomp, no capabilities | own, root-owned, with limits | every call checked in C; the four PIM apps have only their own allow-listed mail requests | network rules and all eight non-network restrictions, in the broker |
| Other built-in apps | inside `lord-server` | no (they are part of the desktop) | `lord-server`'s | no broker; camera, microphone and screen are checked in C | as "LordOS": network rules; camera, microphone, screen and notifications |
| Linux apps from the app launcher | own | none by default; with "no access to your files", their own user, mount and PID namespaces plus Landlock, from the next launch | own, root-owned | no | network rules; camera, microphone, USB, Bluetooth sockets, files and notifications; not the clipboard |
| Terminal programs | children of the Terminal's shell | no | the Terminal's own component scope (0.8.5) | no | as "Terminal": network rules, with the programs' names in the Monitor |
| X11 apps | under Xwayland | as their launcher entry | own, like Wayland apps | no | the same as Linux apps |

A program started some other way, outside the app launcher, is in no app scope and gets no per-app rules. LordOS's own isolation uses neither Flatpak nor bubblewrap (Flathub apps, since 0.8.9.4, run through them inside LordOS's view). In development after 0.8.9.4: Chromium- and Electron-based Flathub apps run too; the sub-sandboxes their helpers ask for are started by a small Spawn helper the launcher forks inside each Flatpak app's view, in the app's own scope, namespaces and Landlock domain, with no capabilities, executing only `flatpak run` of the same app (`docs/FLATPAK.md`, "Sub-sandboxes").

Each `.lpk` app, and the Passwords app, runs as `lord-server --app <id>`: the same binary in "app mode", launched by `lord-server` with a validated package id as its only argument. The process connects to the compositor as a Wayland client and opens the broker socket, then applies the sandbox, and only then loads the app's code (`server/src/sec/sandbox.c`):

- **Landlock** (ABI up to 6): read-only access to the package, the shared app runtime, fonts and libraries; read-write only to `~/.local/share/lordos/appdata/<id>`; scoping of abstract Unix sockets and signals.
- **seccomp-bpf**: an allow list of system calls on every thread (TSYNC), without `ptrace`, `mount`, `kexec`, `bpf`, `perf_event_open`, `keyctl`, module loading or `execve`. New Unix sockets and `socketpair` are refused, because Landlock up to ABI 6 doesn't filter `connect` to named Unix sockets; this keeps the app away from the session bus, the print service and the Wayland socket.
- **No privileges**: `no_new_privs`, an empty capability set and a dropped bounding set.
- **cgroup v2**: `app-lordos-lpk-<id>.scope`, created by root, with `memory.high` 192 MB, `memory.max` 512 MB and one CPU core.
- **Network**: without the `network` permission (declared **and** allowed), seccomp refuses internet sockets and Landlock refuses TCP connect and bind. Network namespaces are not used, because creating one needs privileges `lord-server` doesn't have.

If a kernel feature is missing, the app still starts and the log says which part is missing. The deliberately malicious test app (`tests/lpk-evil`) fails at everything it tries; `build/sandbox-test` passes 14 of 14 checks for apps and 14 of 14 with network. Measured on a VM: about 13.7 MB of RSS per isolated app, a median start of 106 ms, and 0.89 ms to apply the sandbox.

**On the user's own computer (0.8.5).** System Information → Checks → **Run tests** starts the hidden system package `sysprobe` the way any isolated app starts; in app mode, for that package only, `server/src/app/probe.c` takes the same sandbox and tries what must fail: the home folder, `/etc/passwd`, the root cgroup's `cgroup.procs`, an internet and a Unix socket, `ptrace`, a user namespace, `mount` and `exec` (its own data folder must work, as a control). A child forked before the sandbox takes the decoding helpers' profile and tries a socket, `exec`, `fork` and files; and the probe asks its broker for what must be refused (a path outside its folder, the clipboard without permission, the security key, mail). `lord-server` adds what only it can read: the process's `NoNewPrivs`, `Seccomp` and `CapEff` and its cgroup's `memory.max`. On VM 116 every try was refused (9 + 4 + 4), with seccomp mode 2, no new privileges and no capabilities. The probe never gets a permission or a network grant.

### 6.5 The broker, permissions and the file dialog

**Figure: How a permission request travels.**

```
[Isolated app] Asks through the broker socket
    │ request
    ▼
[Broker in lord-server] Looks up the stored decision (perms.c)
    │ state is Ask
    ▼
[System prompt] Only if not decided yet; drawn by the session
    │ shown
    ▼
[You decide] Allow or Don't Allow, saved in permisos.json
    │ answer
    ▼
[Enforced] Broker checks every call; sandbox and kernel block the rest
    │ later
    ▼
[Revocable] Settings → Privacy; camera and microphone stop at once
```

*The app never answers its own prompt: the decision is stored where it can't write, and checked in C on every request.*

The isolated app talks to `lord-server` only over one `SOCK_SEQPACKET` socket. Every request is checked in C: file access only inside the app's own data folder; clipboard reads only with the `clipboard` permission; permission requests answered from the stored decision or, if none, by a **system-drawn prompt** (*Allow / Don't Allow*); camera and microphone only through `lord-server`.

- **Decisions** are stored per user in `~/.config/lordos/permisos.json`, outside the app's reach. The lookup is O(1).
- **The file dialog is LordOS's own powerbox** (`sdk/powerbox.jsx`), not `xdg-desktop-portal`: `lord-server` draws it, opens the chosen file and passes only that descriptor. LordOS implements two desktop portal interfaces itself, in `lord-server` and without `xdg-desktop-portal`: `org.freedesktop.portal.Settings`, for GTK theming, and, since 0.8.8, `org.freedesktop.portal.FileChooser` (`OpenFile` and `SaveFile`, version 2, so browsers keep their own dialog), for Linux apps with no file dialog of their own: it shows this same dialog, inside the home folder, and the answer goes only to the app that asked (`docs/WAYLAND.md`). In 0.8.8 the dialog looks and works like Files, with its sidebar, list and path; local disks mounted for the user are new in it, so an app can now be given a file on one when the person picks it.
- **Microphone:** `lord-server` owns the PipeWire stream and gives the app a read-only shared ring.
- **Camera:** `lord-server` opens the device and gives it only to `lord-media`; the app gets a read-only view of the decoded frames and must acknowledge each one, and `lord-server` validates every acknowledgement.
- **Revocation:** denying the camera or the microphone in Settings stops it at once (the app's `lord-media` is killed; the PipeWire stream is closed). The `network` permission is decided at launch.
- **What is captured now (in development after 0.8.9.4; `docs/PRIVACY.md`).** One green pill by the clock, in every theme and with no setting to hide it, replaces the screen-sharing pills and the camera and microphone dots. Its glyph says what is captured right now, system-wide: a display, a microphone, a video camera, or a display or a camera with a badge for the second. Its panel lists one row per app, with Stop sharing (the share's own stop) and Turn off for this app (the app's permission, or for a Linux or Flatpak app the firewall's restriction), and a live preview of a native app's camera. Its sources are LordOS's own: the screen-sharing API, the ScreenCast and Screenshot portals, `lord.media`, the broker, and the PipeWire guard (§6.6), which now also reports which capture stream a microphone, a camera or a shared screen is linked into and who owns it, after the same checks as its restrictions; an owner it can't name shows as "An unknown program". A program that opens a camera or a sound card itself, without PipeWire, is not shown. Tested by `capture_model_test.mjs` and `pwguard-test`; not yet checked on the VM.
- **Keyring:** an isolated app's keyring requests carry an owner that `lord-server` sets from the verified app id.

**Restrictions beat permissions.** A firewall restriction (§6.6) wins over any stored decision: the request is refused without a prompt, even if the app was allowed before, and restricting a running app takes its camera and microphone away at once, like revoking.

**Limits.** There is no "allow once". Some declared permissions (Bluetooth, launching apps, notifications) have no broker call yet, so isolated apps can't use those capabilities at all; listening on a port is governed by the network permission. A Linux app running as the user could edit the permissions file, unless it is restricted with "no access to your files".

### 6.6 The per-app firewall, its restrictions and the Monitor

**Figure: The path of a connection or a device.**

```
[App opens a connection or a device] connect, sendto, bind, socket, or open() of a device node
    │ system call
    ▼
[eBPF programs in the kernel] cgroup network hooks; cgroup/dev for camera, USB, ALSA capture and /dev/fb; BPF LSM socket_create for Bluetooth. The app is found by its scope
    │ map lookup
    ▼
[Per-app rules] Restrictions first, then the most specific rule, then trusted, then mode
    │ decision
    ▼
[Allow or deny] Denied: the app gets EPERM
    │ ring buffer
    ▼
[Monitor map] New connections, denials and counters, once per second
```

*The decision happens in the kernel when a connection, a socket or a device opens; nothing runs per packet.*

`lord-netperm` enforces per-app rules in the kernel. Linux apps opened from the app launcher run in `app-lordos-<id>.scope`, `.lpk` apps in `app-lordos-lpk-<id>.scope`, and the rest of the session counts as `lordos`. All scopes are root-owned. The service loads seven network programs (`connect4/6`, `sendmsg4/6`, `bind4/6`, `sock_create`), a device program (`cgroup/dev`) and a per-cgroup LSM program on `socket_create` into the cgroup of `lordos.service`, finds each process's app by its cgroup ancestor, and returns allow or deny (`EPERM`). The programs are compiled into the binary and loaded with LordOS's own loader over the `bpf()` system call, which also reads the kernel's BTF to find the LSM hook; libbpf and bcc are not used. If the kernel refuses the device or the LSM program, the network programs still work and the service says so. **Packaging gap on PCs, 0.8.8.6 to 0.8.9.2:** those amd64 packages were built on a machine without clang, so `lord-netperm` had no BPF programs and logged that it enforced nothing (Monitor → Firewall showed it; the Raspberry Pi packages always had them); 0.8.9.3 restores them, and `tools/iso/mkdeb.sh` now refuses to package a `lord-netperm` built without them.

- **Rules** support exact domains, wildcards, IPv4/IPv6 networks, `lan`, `internet`, ports, protocols and direction. Restrictions (no internet, no LAN, no network, no incoming) come first; then the most specific rule wins, with deny beating allow at equal specificity; then trusted apps; then the mode (silent, the default, or off). `npcompile.c` precomputes this into hash and longest-prefix-match maps. A test runs the kernel's decision code against the reference decision maker over 480,000 random connections: 0 differences.
- **Domain names** come only from the system resolver: systemd-resolved's monitor interface or, without it, replies from port 53 of the configured servers read by a receive-only packet socket. Answers an app received on its own sockets are never trusted. So an app that resolves names itself with encrypted DNS (DNS over HTTPS inside a browser, for example) isn't matched by domain rules: an "allow only example.com" rule still blocks it, but a "block example.com" rule doesn't stop it. Address and network rules, the app's default and its restrictions still apply, and Settings says so under the rules.
- **Rules in the interface.** Settings → Privacy → Network rules by app shows each app's default ("allow all" or "block all except rules") and its rules in the order they win, with when each one last matched; the sheet that adds a rule checks what is typed as it is typed. In Monitor → Network, "Allow / Block this domain" on one of an app's destinations opens the same sheet, prefilled with the name the system resolver gave for that address.
- **Escapes.** The cgroup tree is root-owned, so an app can't move itself. A process that asks the user's systemd manager for a new unit (`systemd-run --user`) lands under `user@<uid>.service`; `lord-netperm` attaches the same programs there and holds such processes to the strictest union of that user's running restricted apps. Tested: all escape attempts denied, other users unaffected.
- **Cost**: about 0.5 µs per UDP connect, TCP within noise, no change in throughput, since nothing runs per packet.
- **The Monitor** shows each app's connections (from `sock_diag`, plus ICMP, raw and packet sockets from `/proc/net`) and the destinations the firewall reported recently, bytes, destinations by country from a local database, and a per-app Rule switch. No address ever leaves the machine for lookups: no reverse DNS, no online geolocation.
- **Open connections (0.8.3).** Rules apply to connections already open, not only new ones: the programs also drop packets a rule now denies, and `lord-netperm` destroys those sockets over `sock_diag` (`SOCK_DESTROY`), so a blocked app sees its connections end within a fraction of a second (0.04–0.37 s for TCP and 0.08 s for QUIC on a Pi 5 with the LordOS kernel).
- **LordOS's own components (0.8.5).** Mail and calendar sync, the Store and updates, printers and scanners, the Terminal and the blocklist updates each run in a scope of their own, so each can be seen and blocked separately; their sockets are opened by a small connector that `lord-server` re-executes with fixed arguments, which enters the component's scope and hands back only a connected socket. A connector (`lord-server --net-connector mail|print|lists`) has a fixed argument list and environment, `no_new_privs`, isn't dumpable, answers only fixed-size requests (family, type, address, port) with no names, paths or execution, and fails closed: if it can't enter its scope it exits and the request fails. The Store's download child enters its own scope in the same spirit before dropping to `nobody` (§6.3). Name resolution, time synchronization, the network service and VPN tunnels are shown and never blocked; blocking the Store asks first, because security updates stop. In 0.8.7 a fourth connector, `lan`, approved by the maintainer on 2026-10-31, gives Files → Network its own row (`lordos:lan`, `lordos-net-lan.scope`), with the same fixed-size requests and no new request type; connectors can't tell ports apart, so `lan.c` is what bounds the search. Remote Desk and the remote folders are firewall apps of their own, `desktop:lordos-rdesk` and `desktop:lordos-rclone`, and the launcher refuses a `.desktop` file with either id, so none can inherit their rules. In 0.8.8.7 a fifth connector, `sql`, gives Databases its own row (`lordos:sql`, shown as "Databases" in the firewall and the Monitor): it connects only to the host and port of a saved favorite, named by its id, never to a host JavaScript gives. In 0.8.9 a sixth connector, `weather`, gives the weather widget its own row (`lordos:weather`, `lordos-net-weather.scope`) and connects only to `api.open-meteo.com:443`, and `lord-stream` runs in a scope of its own, `lordos-net-streams.scope`, shown as "Cameras & TV" (`lordos:streams`), so cameras and TV channels can be seen and blocked apart from the rest of the desktop.
- **Blocklists and "deny silently" (0.8.5).** Public lists of advertising, tracker, malware and attacking sites (each with its source and licence) are downloaded over HTTPS once a day by `lord-fetch`, a helper with no sockets of its own and the certificate checked against the system's authorities, and every line is validated again; a rule the user writes for a site always wins over a list. A new firewall mode, "deny silently", lets only what a rule allows connect and records the rest, while the computer's own services keep working. An optional menu bar item shows the traffic rates and what was recently denied.

**Restrictions beyond the network.** Besides the four network restrictions (no internet, no LAN, no network, no incoming connections), the owner can restrict an app from the camera, the microphone, the screen, USB, files, the clipboard, Bluetooth and notifications. Each one is enforced where the resource is handed out, checked against the app's scope and never against a name the app gives itself, and it beats any permission granted in `permisos.json`.

**Figure: Where each restriction is enforced.**

```
Broker in lord-server
    Isolated apps (.lpk, Passwords, Mail, Calendar, Contacts, Reminders): all eight restrictions, refused without a prompt
        │
App launcher
    Linux apps, no access to your files: own user, mount and PID namespaces, a tmpfs home and Landlock, from the next launch
        │
Notification server (notifyd)
    Linux apps' notifications: the sender's identity comes from the bus; failures drop it
        │
PipeWire guard (pwguard)
    Microphone and camera through PipeWire: identity from the socket's credentials, applied live
        │
lord-netperm's eBPF programs in the kernel
    Network hooks; cgroup/dev for camera, USB, ALSA capture and /dev/fb; BPF LSM socket_create for Bluetooth sockets
```

*Each restriction is checked where the resource is handed out, against the app's root-owned scope, never against a name the app gives itself.*

| Restriction | `.lpk` apps and Passwords | Built-in apps ("LordOS") | Linux apps from the app launcher |
|---|---|---|---|
| camera | broker (`brokercam.c`) | `js_media.c` | `cgroup/dev` on V4L2 nodes, and the PipeWire guard |
| microphone | broker | `js_media.c` | the PipeWire guard, and `cgroup/dev` on ALSA capture nodes |
| screen | broker (no capture API in app mode) | `js_media.c` | by design: no capture protocol and no X server; in 0.8.8.8 the ScreenCast portal refuses the app before any question and the PipeWire guard hides every shared screen from it; `/dev/fb*` denied. Only a packaged app of a Verified author (0.8.8) may ask for the separate screen-sharing API, behind a system prompt and an indicator (`docs/SCREEN-SHARING.md`) |
| USB | broker (the security key of Passwords) | not offered | `cgroup/dev`: raw USB, hidraw and USB serial nodes |
| files | broker (file picker, camera saves) | not offered | the launcher: own namespaces, a tmpfs home and Landlock, from the next launch |
| clipboard | broker | not offered | not available |
| Bluetooth | broker (no Bluetooth API in app mode) | not offered | BPF LSM program on `socket_create`: no `AF_BLUETOOTH` sockets |
| notifications | the `notifications` permission | `sdk/notify.js` | `notifyd`, by the caller's verified identity |

For isolated apps the broker (`sec/restrict.c`) is the single enforcement point: a restricted request is refused without a prompt, and restricting a running app takes its camera and microphone away at once (`tests/broker_restrict_test.c` covers every restriction, with and without it). The "LordOS" row is the desktop itself (Files, copy and paste, Disks, Bluetooth settings), so it doesn't offer files, USB, clipboard or Bluetooth; individual apps are restricted instead. For Linux apps:

- **Devices.** In cgroup v2 the device controller is a BPF program. `lord-netperm`'s refuses `open()` and `mknod()` of the device classes the app is restricted from (V4L2, raw USB, hidraw, USB serial, ALSA capture nodes, `/dev/fb*`) and allows everything else. It applies to the next `open`; a descriptor already open stays usable.
- **Bluetooth sockets.** The inet socket hook never sees `AF_BLUETOOTH`, so a per-cgroup LSM program on `socket_create` refuses them.
- **Files.** Right before `execve`, the launcher's child enters its own unprivileged user, mount and PID namespaces. The home folder is an empty tmpfs holding only the app's own folders (derived from its desktop id, never from fields a `.desktop` file controls) and the file it was opened with; the runtime folder holds only the Wayland and sound sockets, so the session bus and the user's systemd are out of reach; then Landlock limits the rest. It applies at the next launch. GTK apps, Firefox and Chromium run without their D-Bus integrations.
- **Notifications.** `notifyd` asks the bus for the caller's PID (only an answer the bus itself sent counts), finds its app scope, and drops the notification of a restricted app; an error or a late answer drops it too (fail closed).
- **Microphone and camera through PipeWire.** The PipeWire guard (`sec/pwguard.c`), `lord-server`'s own PipeWire client, identifies each client by the PID PipeWire took from the socket's credentials and, for a restricted app, hides capture nodes and destroys its capture streams within a second, a recording already running included. While a restricted app runs, a client whose identity can't be established is treated as restricted.

**Limits.** "Ask" mode is designed but behaves as silent today. ICMP is blocked only by "no network"; connections to an already-open port aren't checked. The restrictions for Linux apps don't cover:

- BlueZ over D-Bus: a Bluetooth-restricted app can still ask `bluetoothd` on the system bus to scan, pair and connect;
- the system bus, which stays reachable even with "no access to your files";
- the clipboard;
- apps started outside the app launcher, which are in no app scope;
- side effects of the `user@` union: while a restricted app runs, the user's own services are held to the same union (a headset's call audio, which PipeWire opens per call, stops for that time);
- a window of a few milliseconds in which a new PipeWire client of a restricted app has full permissions, or in which a capture stream can receive audio before it is destroyed.

### 6.7 Helpers that process untrusted data

**Figure: Opening an untrusted file.**

```
[App asks to open a file] PDF, archive, video, photo, mail
    │ request
    ▼
[lord-server] Validates the path and opens the file
    │ file descriptor
    ▼
[Sandboxed helper] Parses with FFmpeg, Poppler, libarchive or OpenSSL; no network, no exec
    │ sealed memfd
    ▼
[Sealed shared memory] Pixels or pages, validated by lord-server
```

*A malicious file can crash its helper, but the helper can't reach the network, run programs or open other files.*

`lord-doc` (PDF, archives, fonts, scanner images), `lord-media` (video, audio, photos, camera), `lord-maild` (mail, calendars, contacts), `lord-vault` (secrets) and, since 0.8.5, `lord-fetch` (the firewall's blocklists) and `lord-tls` (HTTPS for the package engine) share one hardened sandbox, `sandbox_apply_helper()`:

- no `socket`, `socketpair`, `connect`, `bind`, `listen`, `accept`; no `execve`; `clone` only for threads; seccomp on every thread, and if seccomp can't be applied the helper exits;
- files only through descriptors passed by `lord-server`; ioctls only by class (DRM, V4L2, DMA-BUF) where needed;
- results returned in sealed shared memory, validated by `lord-server`.

`lord-media` doesn't even receive the PipeWire socket; audio flows through a shared ring whose stream belongs to `lord-server`. `lord-maild` can't create sockets: it asks `lord-server`, which connects only to servers in the accounts file (and, after the user asks to load images, only to public addresses on ports 80/443 for ten minutes) and hands over the connected socket. `lord-fetch` and `lord-tls` have no sockets of their own either: each receives one socket already connected (by the `lists` connector, or by the Store's download child), checks the server's certificate against the system's authorities and its host name with TLS 1.2 or later, and is never relaxed; `lord-fetch` makes one HTTP GET of at most 16 MB, parses the list strictly and sends redirects back to `lord-server` (at most three, https only), which validates every line again. `build/sandbox-test helper` passes 17 of 17 checks.

In 0.8.7, two more helpers take the same sandbox. `lord-clean`, Cleaner's scanner, is read-only and refuses to run without Landlock: `lord-server` passes each root as an open folder, and it walks with `openat2` so that links and mounts can't lead it out; it also decodes the images for similar-image search, which `lord-server` never does. `lord-lan` follows `lord-fetch`'s rules: no sockets, no files, libc only, and it never chooses where to connect. It reads what the local network answers with LordOS's own SMB2, NTLMSSP, DCE/RPC and ONC RPC parsers, tested with `build/lan-test` under ASan and UBSan against 40,000 damaged answers, and `lord-server` parses its answers again.
`lord-rdesk` takes the same sandbox one step later: it resolves and connects first, then applies it, so from there on it has no new sockets and no `exec`, with `/etc/ssl`, `/usr/lib` and the certificate folder read-only for RDP alone. It paints BGRA into a shared memory file whose size is sealed; `lord-server` takes at most 256 messages per poll and never blocks on it, and its scope has `lord-server`'s memory limits (256 MB high, 512 MB max). A folder shared over RDP is opened before the sandbox and is read-only by the sandbox's rule, not the library's promise, unless the user made it writable.

`lord-media` has one wider path in 0.8.7. Raspberry Pi's FFmpeg, pinned on the Pi, opens the HEVC decoder by path, so for that one job, playing with `v4l2request`, the helper may open two exact device files found from sysfs before the sandbox, reads `/sys/class`, `/sys/bus` and `/run/udev`, and gets the V4L2 and media controller ioctl classes. Sockets and `exec` stay refused. It still receives its input as an open file. A moving wallpaper plays hardware-only: if the decoder doesn't start or fails, `lord-media` stops and the still image stays.

**In 0.8.8.6** two more helpers take the same sandbox, each the only binary that links its library (`docs/ARCHITECTURE.md`). `lord-ocr` is `lord-doc`'s helper loop built with Tesseract only: it receives the cropped pixels in a sealed memory file, never a path, reads only `/usr` (the language data), runs one thread, and language names are checked in `lord-server` and again in the helper; `server/tests/ocr_test.sh` checks that it can't read `~/.ssh` or the home folder, write `/tmp`, reach the network, make sockets or fork. `lord-tts` is the same loop built with audio.cpp and ggml: it reads `/usr`, its libraries and the models folder it gets as a descriptor, writes only `~/.cache/lordos/voice`, has no network, sockets, fork or exec, and reads a voice file as untrusted data, checking every size. On the graphics card only, it may open the render node with DRM ioctls and list `/dev/dri` without opening anything else there (a new read-directory-only Landlock rule), never the display node `lord-server` drives; `server/tests/tts_test.sh` checks the confinement in both modes. `lord-say`, which `lord-server` starts to read aloud (§1.2), holds no speech code: it gets the text on a sealed memory file, writes the audio's 16 band levels on a descriptor for the player, and saving goes to a file `lord-server` creates with `O_EXCL` in the folder the user chose and renames at the end, so `say` never sees a path. Isolated apps have no `lord.voice`.

**In 0.8.8.7** two more helpers take the same sandbox (`AGENTS.md`). `lord-sftp` speaks SFTP for the Terminal's Files mode: it receives the channel `lord-server` opened on the tab's own `ssh` control socket and the local file as descriptors, never a path, with no `clone`, socket, `connect`, `bind` or `exec`. `lord-server` uses only that tab's socket, and remote commands come from a closed list (`file -b --`, `sha256sum --`, `sudo -n <sftp-server>`) with their arguments checked in C; a `sudo` password is written to that channel and wiped, never kept and never given to JavaScript. Names with `/` or control characters, and odd owner names, are left out of listings. `lord-sql` is one process per Databases connection: it gets the connected socket from the `sql` connector (or from `lord-server` for a local Unix socket), loads the certificate authorities and applies the sandbox before it reads a byte from the server, with no sockets of its own and no files. It speaks the MySQL protocol itself (TLS, `mysql_native_password` and `caching_sha2_password`), parses everything a server sends with bounds checks, and sends a password as such (MySQL 8's first login of a user) only over TLS whose certificate was verified or trusted by fingerprint. Values written back into SQL quote `'` as `''`, which no stored value can turn into the end of the string under any `sql_mode`. Tests: `build/sftp-test` (the multiplexing and SFTP wire against hostile bytes, `lord-sftp` against a fake server) and `build/sftpc-test` (`lord-server`'s side end to end with real OpenSSH as the user: a private `sshd` and an `ssh` master), `build/sql-proto-test`, `build/sql-e2e-test` (`lord-sql` against a fake MySQL server: both sign-in methods, RSA, TLS, results) and `build/sqlc-test` (the favorites file and the connection rule).

**In 0.8.8.8** the Terminal adds no helper. Its port forwards, the uploads dropped on a pane and the downloads from `ls` use the same control socket, the same `lord-sftp` and the same checks as Files mode; a forward listens on 127.0.0.1 only, and its host and ports are checked in `lord-server` (`build/sftpc-test` opens one to the test server's own `sshd`, reads its banner through it, and refuses a host with a space). The directory a remote shell reports is the server's output, so it is kept only as an absolute path with no control characters, and it only chooses where on the server a file goes or comes from. Links in what is uploaded are never followed, a name on either side is never replaced unasked (Edit's saves to the file chosen for editing are the one exception), and the copies that Open and Edit bring down stay in `~/.cache/lordos/terminal-remote`. The first desktop-parity items of 0.8.8.8 add no helper and no broker message either: file lists from drags and from the clipboard are taken only from Wayland clients that are positively unsandboxed and only as local `file://` paths, a file list pasted in Files asks first, `lord.primary.get()` answers only while a middle-button press is handled, and `lord.mpris` and `lord.sni`, which talk to other apps over the session bus, exist only in the desktop's own context, never in an isolated app, with every string cleaned and every call asynchronous.

Later in 0.8.8.8 one helper and one runtime are added, both approved by the maintainer (`AGENTS.md`). **`lord-screencast`** makes the PipeWire stream of a shared screen or window. It gets its PipeWire connections already connected and the frames through a sealed memfd ring, applies `sandbox_apply_helper` (scope `lordos-screencast`; its only extra syscalls are the three `timerfd_*`, with no socket, `connect`, `bind`, process `clone` or `exec`) before the connection speaks, and lowers its own PipeWire permissions to read-only except on its own nodes. Each side checks every message of the other (`build/castproto-test`, with ASan and UBSan). **`lord-media`** also rasterizes SVG icons with vendored nanosvg, on an fd `lord-server` opened, with limits on size, elements, nesting, shapes, points and numbers, and 3 s before the worker is killed (`build/svgrast-test`, `build/media-test svg`). **`lord-web`** is not one of these helpers. It is a separate program, in an optional package, whose web content runs under WebKit's own sandbox. `lord-web` itself gets its own firewall scope, a cgroup with limits, Landlock's scoping and `no_new_privs`, refuses to start without them inside a LordOS session, and refuses any registry file it doesn't fully accept (`build/webapp-test`). Two automated security scans of the branch and the review of each feature found these problems, all fixed before any release: a container that could pose as a Flatpak app for the shortcuts permission (a Flatpak identity now also needs Flatpak's own record outside the sandbox), a slot counter that could go negative, a use after free in the X drag code, a DmaBuf that `lord-web` freed while its import was unanswered (reachable by a compromised renderer), markup hidden from the SVG limits, X drag data taken from a forged `SelectionNotify`, a share that could follow a reused window id, and probe redirects to local addresses.

**In 0.8.9** two helpers and one more job are added, each approved by the maintainer (`AGENTS.md`). **`lord-stream`** (approved 2026-11-16; `docs/MEDIA.md`, "Network streams") is `lord-media`'s own player built as a second binary for the Video widget and the Player's Streams: RTSP, RTMP, SRT, RTP, UDP (multicast included), HLS, MPEG-DASH, HTTP MPEG-TS, MJPEG and M3U lists. It is the only helper with network: `sandbox_apply_helper` gains a `network` flag that lets `socket` create only `AF_INET` and `AF_INET6` sockets, plus `connect`, `bind` (RTP ports, multicast) and `sendmmsg`/`recvmmsg` (glibc's resolver), and never Unix, netlink, `socketpair`, `exec` or `fork`; Landlock leaves it the libraries and the files name resolution and TLS read, read-only. `lord-media` itself still has no network and refuses the M3U job. Addresses are checked in `lord-server` and again in the helper (printable ASCII, at most 2048 bytes, a closed list of schemes), FFmpeg's `protocol_whitelist` holds network protocols only (never `file`, `pipe`, `concat` or `data`), every open and read is bounded (20 s to open, 6 s without data), M3U channels are rebuilt and checked again by `lord-server` before JavaScript sees them, and a password in an address goes to the keyring and travels only inside the job. **`lord-hidpp`** (approved 2026-11-17, battery reads only; `docs/DEVICES.md`) gives the exact percentage of Logitech mice and keyboards that the kernel reports only as a level. It is installed `root:lordos-hidpp 2755`, a group no person is in, and `packaging/udev/72-lordos-hidpp.rules` gives that group only the hidraw nodes of the kernel's `logitech-hidpp-device` driver, never a receiver's node, so nothing can be paired or unpaired through them. It takes no arguments and reads no environment; it opens those nodes (each checked against the device number sysfs gives), drops the group for good and checks it can't get it back, applies the helpers' sandbox with no network, files or ioctls, and only then asks each device for three battery features (0x1004, 0x1000, 0x1001), never a write that changes a device; it prints only numbers, which `lord-server` checks before it finds the device in sysfs itself, at most once a minute (`tests/hidpp_test.c` against a fake device). On the maintainer's MX Master 3 and MX Keys, Battery Status gives steps (50 %, 20 %), not a fine percentage. **`lord-fetch`'s second job** (approved 2026-11-16) is the weather: two numbers `lord-server` takes from its own city list or tzdata, never from JavaScript, a socket the `weather` connector opened to `api.open-meteo.com:443` only, one GET path the helper builds itself, no redirect, at most 64 KB parsed strictly into numbers and read again by `lord-server` (`fetch/weather.c`, `build/weather-test`). The sandbox's Landlock rules also work for single files now: a file such as `/etc/ld.so.cache` got directory rights, the kernel refused the rule, and files in the helpers' lists were never readable (`build/sandbox-test helper-net`).

**The Claude Security review of the 0.8.9 branch** found four problems, all in code new in this version and all fixed before any release: streams checked no TLS certificate, since FFmpeg verifies only when asked, so an https, HLS-over-https or rtmps camera or channel accepted any server and a camera password from the keyring could reach someone in the middle (`lord-stream` now asks for the certificate against the system's authorities and the host name on every open, nested HLS and DASH opens included, `lm_tls_verify` in `media/helper/lm_io.c`, and a self-signed server fails); the https M3U download checked none either (`media/stream/ls_m3u.c`); `lord-server` leaked a parsed list when `lord-stream` sent JSON that wasn't an array; and a use after free in `lord.setProp(id, 'wave', …)`, where a getter on the object could destroy the node while it was written: the values are now read first and the node looked up again by id and serial, and `lord.setStyle(id, 'gradient', …)` and `setProp`'s key are fixed the same way (`ui/js.c`; `tests/js_getter_destroy.sh`, found with AddressSanitizer on the old code). rtsps can't be checked: FFmpeg 7.1's RTSP demuxer passes no TLS options, so an rtsps camera is encrypted against someone listening but not protected from someone in the middle, the same as plain rtsp (`docs/MEDIA.md`).

**Machines in development after 0.8.9.4 (`AGENTS.md`).** Windows 11 machines bring three approved pieces. Debian's `swtpm`, one per machine, started by `lord-vm` as the person, never as root, in its jail: no socket, writing only its state folder, its own seccomp, 64 MB and half a CPU. The LordOS tools for Windows, built by LordOS with mingw-w64, installed only through the guest agent after a SHA-256 check and run as the signed-in person: they open only a file whose random token, size and SHA-256 match a fresh copy step (never a path from this computer), and the host can launch only a program the guest listed. And downloads the catalog pins (`vm-image-get`: Microsoft's evaluation, virtio-win, WinFsp), each by https URL, SHA-256 and size. A 3D Linux machine's QEMU may open only the GPU's render node, never the primary card node. A guest is untrusted: every frame of its tools is parsed to its last byte, with random-input checks in `vm-test`, and the clipboard rules of §5.1 keep data out of a machine until something there pastes. Security reviews of this work found problems in the clipboard and sound paths (a guest raising the paste question under a click on its way, a preview swapped after a yes, a machine's input set to an output's monitor, a password manager's secret leaving the guest), all fixed before any release.

**Logs (0.8.8.8; `docs/SYSTEM.md`, "Log files").** Every LordOS log moves to `/var/log/lordos`: the root daemons' files there (`lord-sessiond`, `lord-netd`, `lord-fand`, the administration helper, which also still write to the journal), and one folder per user, `users/<user>`, mode 0700, with the session's (`compositor.log`, `shell.log` for the shell's JavaScript, `xwayland.log`, `cloud.log`), one file per app under `apps/` and one per web app and profile under `web/`. `lord-sessiond` makes that folder at login as root, step by step from folders opened without following symlinks, the two above it root's and writable by nobody else, and hands it to the user with `fchown`/`fchmod` on its own descriptor; a symlink, a file or another user's folder in its place is refused and never changed, and root touches nothing inside. A nested or development `lord-server` keeps to `~/.cache/lordos`. Lines carry a time, a level and a subsystem, stamped by a small child that reads the program's stderr through a pipe and drains it after a crash; the previous session's log is kept as `.prev` instead of being truncated at login. `/etc/logrotate.d/lordos` rotates only the root daemons' files, daily, keeping 7 compressed copies; it has no rule inside the users' folders, where a user could swap a subfolder for a symlink while it runs. Every file is capped at 16 MB by its own writers, as its owner (the older part goes to `.old`, so a noisy session never overwrites the previous one's `.prev`), and an isolated app writes to a pipe that a `lord-log` child copies into its file, checking the cap after every megabyte, so the disk never fills. Checked: `build/lordlog-test` (symlink tricks in a temporary folder, the cap, the format, the stamping child end to end, a noisy session keeping the previous one, an app writing 19 MB in a loop).

**Connections to other computers (0.8.7; security review of 2026-11-01).** What stands in the way of a server the user connects to, and what is left:

| Threat | What stands in the way | What is left |
|---|---|---|
| An RDP server takes a password | Only TLS and NLA are allowed; no credential goes to a server that picks RDP's own security (`tests/rdesk_rdp_test.c`) | RDP to a real session of a desktop system isn't verified |
| A TLS certificate changes (RDP, ftps, https WebDAV) | An unknown or changed certificate shows its fingerprint, both of them when changed, and the person decides; for remote folders an accepted certificate is checked before the system's verdict, so a different one is refused even if a public authority signed it | A self-signed certificate must name the host it's used for |
| An SFTP host key changes | Every key kept was shown first and an answer counts only for the fingerprint on screen; a different key is refused; rclone checks the same file on the real connection | The first connection rests on the person comparing the fingerprint |
| A VNC server skips the password | A server that offers only "None" when a password was given is refused, and the app says the connection isn't encrypted | VNC's DES is required by the protocol and weak; the traffic is not encrypted |
| An SMB server is impersonated | The sign-in carries a target name and a MIC, the server must sign its final answer, and a session marked guest after a password counts as refused | Later answers are shown, not trusted: their signatures aren't checked |
| A server's bytes attack a parser | `lord-lan` and `lord-rdesk` are sandboxed, the VNC client has a fuzz run, and `ssh-keyscan`, `openssl` and `rclone obscure` run read-only (Landlock) with a 15 s limit | `rclone mount` has no sandbox beyond its scope; without Landlock only the scope and the deadline hold |
| A password leaks | It reaches each helper in one message and is wiped; the keyring keeps it only if asked; rclone's configuration is a memory file, on no command line or environment | The obscured password is readable by the session user's own processes while mounted; plain ftp and http WebDAV send it readable, and the sheet says so |
| A program takes a helper's firewall rules | The launcher refuses a `.desktop` file with either id (§6.6) | |
| A hostile or swapped wallpaper | The size and SHA-256 of the signed catalog, and `lord-media`'s sandbox | A user's own video has no catalog hash |

### 6.8 Package signing and trust levels

`.lpk` packages carry a manifest of every file's SHA-256 and an Ed25519 signature over it. SHA-256 and Ed25519 are LordOS's own code (Ed25519 following TweetNaCl's arithmetic), tested against NIST and RFC 8032 vectors (55 of 55). Verification happens in C at install and at load. The Store shows the trust level: **LordOS** (official key, compiled into the binary so no file can add one), **Verified author** (listed in the signed catalog), **Signed by <name>**, or **Unsigned** with a warning. Updates must be signed with the same key. A signed catalog carries a revocation list. If you edit an installed app, LordOS marks it "Modified by you", can restore the original, or can share your version signed with your own key, with credit to the original.

**Status:** official `.lpk` packages are still signed with a development key, until the final key replaces it. A signed LordOS app repository for `.lpk` apps is not built yet; LordOS itself updates from a signed APT repository (§6.9).

### 6.9 Release signing

Every release file (the `.deb`, the ISO and the Raspberry Pi image) is listed with its SHA-256 in `SHA256SUMS`, and `SHA256SUMS` is signed with the LordOS release key (Ed25519). The public key is `tools/release/lordos-release.pub.pem`, also embedded in the Debian installer. Its fingerprint (SHA-256 of the DER public key) is:

`c7155b8e6bbbb180f907381994d06af76d333016cd6f3facf67cadd053ea108e`

The private key lives only on the maintainer's machine, never in the repository or on a build machine. Each release also carries an SPDX 2.3 software bill of materials (SBOM) per architecture, listed in `SHA256SUMS` and so covered by the signature (as each image's list of source packages is, for images built from 0.8.8.9 on, §12), and its release notes come from `CHANGELOG.md`, kept in the Keep a Changelog format. §11 shows how to check a download.

- **The APT repository (0.8.1).** `lordos.org/apt` is a signed APT repository built and signed only on the maintainer's machine; installed systems update from it. On the Raspberry Pi 5 it also mirrors the bootloader updater and the few Raspberry Pi packages it needs, copied only after their signature and every file's SHA-256 match a pinned list (0.8.4.1).
- **LordOS's own code is verified before it runs (0.8.2).** Every JavaScript bundle LordOS runs as its own code (the themes, the app host, the system apps) is loaded only through `codesig_load`, which checks it against `code-manifest.json` and its Ed25519 signature by the release key. A modified bundle is not loaded and the user sees why; System Information's Checks report it (§11.4). Development builds without a signed manifest say so.
- **The tested-hardware snapshot (0.8.7).** System Information's Compatibility panel reads a snapshot signed with the release key on the maintainer's machine, in its own package, `lordos-hwdata`, which can be updated between releases. `lord-server` verifies the signature in C before the panel shows any of it (`docs/SIGNING.md`). So far it holds one accepted community report (#42); every machine reported, accepted or not, is listed in [`docs/HARDWARE-REPORT.md`](https://github.com/lordbasex/LordOS/blob/main/docs/HARDWARE-REPORT.md).
- **System apps can't be removed** from the Store (0.8.2).

### 6.10 The vault

`lord-vault` keeps passwords and the session keyring in `.lvault` files: one random 32-byte vault key, wrapped once per unlock method (Argon2id password with a cost calibrated per machine, FIDO2 `hmac-secret` with LordOS's own CTAP2 client, key file, password plus key file, recovery key); content sealed with XChaCha20-Poly1305 with the whole header as associated data; attachments sealed separately; atomic saves with a backup. Every flipped byte and every truncation is detected (1,165 of 1,165 in the test). Secrets live in an `mlock`ed arena excluded from core dumps and wiped on free, in a process that is not dumpable. The Passwords window runs in its own sandboxed process, so revealed values never enter the desktop's JavaScript. The keyring opens at login with the password `lord-sessiond` verified, and serves Linux apps through LordOS's own Secret Service implementation. Since 0.8.5 the session starts only once the user's session bus exists (§3.6), so `org.freedesktop.secrets` and `org.freedesktop.Notifications` belong to the LordOS session from the first second; and when an app pulls in gnome-keyring, a drop-in shipped by the lordos package (`gnome-keyring-daemon.service.d/lordos.conf`) keeps only its PKCS#11 component, so LordOS's keyring keeps the Secret Service and no second "choose a password for the new keyring" window appears. Tested on the VMware machine after a reboot with automatic login: both names belong to the LordOS session, and Chrome asks through LordOS's own keyring prompt. When several apps ask at once, one answer in the keyring prompt now goes to all of them. Real hardware security keys are not yet tested. Since 0.8.8.6 the Terminal fills and saves passwords without JavaScript seeing them, two exceptions approved in `AGENTS.md`. When a program asks with echo off and a prompt that names a password, a login the user picks goes from `lord-vault` to the terminal in `lord-server`'s C code on the private channel, written only while the program is still asking. A password typed to ssh, git, a database client and similar programs is kept in one locked page (`mlock`, `MADV_DONTDUMP`), wiped on every way out (rejected, Ctrl+C, declined, saved, closed, or after 60 s) and offered for saving once the program accepts it, never for the user's own login password (`sudo`, `su`, `passwd`, `pkexec`) or while the process is traced; JavaScript gets only the program, host, user and a random token (`build/term-secret-test`; `build/term-capture-test`, 28 checks, also under ASan and UBSan). Mail's account passwords now wait for a locked keyring and are answered once it opens, instead of being asked for again at every boot.

**Across LordOS (0.8.8.7).** The password fields of Settings → Cloud, Files' shared-folder sign-in and Connect to Server (sftp, ftp, WebDAV), Remote Desk and Databases have Passwords' 🔑, as Wi-Fi already did. For a server it lists only entries whose host field or site is exactly the address the password goes to, never a guess from a title and never the name a machine announces on the local network, so a device can't take a kept server's name and be offered its password; the password leaves Passwords only when one is picked, while Passwords is unlocked. When a server accepts a password typed in the form, the app asks whether to save it in Passwords, and nothing is saved until Save is chosen. Isolated apps (Mail, Calendar, Contacts, Reminders) can still use only their own keyring items. A copied password shows how many seconds it has before it is cleared, with Keep; `lord-server` tells Passwords only whether its own copy is still on the clipboard, never what the clipboard holds, only for a few seconds after the copy and not under the firewall's clipboard restriction. The isolated apps can now paste: a paste the person asks for in the app's window (Ctrl+V or Shift+Insert, which `lord-server` sees reach it, or the clipboard panel) lets that app read the clipboard once within 2 seconds; the app can't fake the keys, and any other read still needs the permission (#64).

### 6.11 Protected windows

A window marked protected (Passwords is) is painted black in every path that copies pixels out: screenshots, recordings, thumbnails, the remote desktop, and Wayland menus and fullscreen. The real monitor shows it normally. Linux apps have no screen-capture protocol to begin with. Since 0.8.2, keys typed into LordOS's own prompts (the keyring, administrator passwords) never reach the Linux app in front. In 0.8.7, the on-screen keyboard's panel and System Information's window while serial numbers are showing are protected the same way.

### 6.12 Disclosure and standards

Vulnerabilities are reported as described in `SECURITY.md`, with a machine-readable contact at `https://lordos.org/.well-known/security.txt` (RFC 9116). LordOS's processes are **aligned with, not certified against**, ISO/IEC 29147 and ISO/IEC 30111 (vulnerability disclosure and handling), ISO/IEC 5230 (OpenChain license compliance: the inventory in `THIRD_PARTY.md`, the license notices and the SBOM) and ISO/IEC 18974 (OpenChain security assurance: the SBOM plus Debian's security updates for the packages LordOS depends on). lordos.org publishes the legal and trust pages (security policy, code signing, licenses, privacy, support lifecycle, standards) and says what is still missing: no formal self-certification, no automated matching of the SBOM against vulnerability databases, no SBOM for the whole images, and no third-party audit.

### 7.1 Memory and idle

**Two different magnitudes.** The first rows measure the **whole system**: the "used" column of `free`, which is everything the kernel, Debian's services (systemd, journald, udev, the network, PipeWire, CUPS…), LordOS's root services and the user's session hold, without the page cache the kernel can give back. The other rows are the **resident memory (RSS) of one process**, as `ps` or `/proc/<pid>/status` report it. An RSS is not the whole system's consumption, and RSS figures can't be added up: pages of shared libraries are counted in every process that maps them. Comparing LordOS with another desktop means comparing `free`'s "used" on the same machine, after the same time idle, with the same apps open; a fair split of the shared pages per process is PSS (`/proc/<pid>/smaps_rollup`). ### 7.2 Drawing

- **Software vblank (0.8.5).** A virtual card that completes page flips at once (VMware's `vmwgfx`) made the compositor and its apps draw 500–580 frames a second on a 60 Hz display; LordOS now detects it and paces frames to the refresh on a fixed grid: 59.8 frames a second, p99 18.4 ms, no frame over budget (`results/0.8.5~rc1-beta/vmware-fusion`). On the released 0.8.5-beta, the Test Bench with its 3D view on the same machine measured 59.83 frames a second over 1,796 frames, p99 17.9 ms, one frame over budget, 1,795 presented (`results/0.8.5-beta/vmware-fusion`). The same grid also paces sessions without a monitor, so waiting in whole milliseconds no longer turns 60 frames a second into 57.
- **Dragging on the GPU path (0.8.5 fix).** A dragged window is painted from a cached layer; on the GPU path every fully transparent pixel of that layer was taken for a Linux window's hole, and now only pixels inside an app surface are. In 0.8.5-beta small black squares could still show at a dragged window's rounded corners, on the CPU and GPU paths: the layer's corner restore took the saved pixel as opaque. In 0.8.6 it mixes both pixels alpha included, so the layer stays transparent outside the curve; a test compares each corner with a full repaint on both paths.
- **A cheaper drag frame (0.8.6).** A dragged window's frame now paints only the part of its layer that changed and only the changed part of what is below it, with the same pixels: 2,417 recorded frame hashes per path must match, and the one approved change brings rounded corners below the window one level closer to a full repaint. On the GPU path the window itself can be composed by the GPU with the CPU's exact arithmetic, after a self-test of every pixel combination ("GPU drag"), and the next frame can be painted while the previous flip is pending; both were measured on the Raspberry Pi 5 and were off by default in 0.8.6. In 0.8.7, GPU drag covers the whole drag and is on by default, verified on V3D and SVGA3D only. Results on the Raspberry Pi 5 are in §7.4.
- Dragging a window on one 1280×800 display on the CPU path: about 6.7–6.9 ms of work per frame, around 120 frames per second (VM 118, `docs/DISPLAYS.md`).
- The same window on a 2560×1600 display at 150 %: about 5.1 ms per frame.
- Video: painting straight from the decoded frame when only an opaque video changed brought `lord-server` from 42 % to 13 % of a core for a windowed 1080p video, and from 92 % to 15 % fullscreen (`docs/ROADMAP.md`, media).
- The Monitor closed costs nothing: its sampling thread doesn't exist until opened (`docs/MONITOR.md`).
- **The CPU path in 0.8.5** (VM 116, no GPU, screen composed on the CPU, viewed through the remote desktop from a browser with a 60 Hz screen; `docs/REMOTE.md`, "Measurements (0.8.5, CPU reference)"): the backdrop blur of a window (radius 20) went from 27.7 ms to 6.0 ms on one thread and 2.7 ms on eight, with identical pixels; a 1280×800 test scene from about 18 to 55–58 frames a second; a 1920×1080 session playing a 60 fps clip from 45 (one core at 100 %) to 55–58 frames a second on the thread pool. A 1080p, 24 fps video in the browser played in real time with no frame dropped by the player over 17 s. The software H.264 encoder takes 12–13 ms a frame at 1280–1568 px wide, so it tops out near 75–80 frames a second. AV1 at 60 fps remains the hard case without a GPU: the browser decodes it in software on the same machine that composes the screen.
- **A folder of photos in Files (0.8.8.7; #71, #82).** Each JPEG or PNG icon used to be the whole picture, decoded on the interface thread and kept until the session ended (48 MB for a 12-megapixel photo). With 1,520 12-megapixel photos, `lord-server` went from 10 GB in 23 seconds (then killed) to 265 MB at most, with no pause over 0.4 s; with 300 of them it holds 154 MB once the thumbnails are made. A big folder of videos no longer keeps the desktop busy either: each thumbnail is asked for once and an answer redraws only the items that show it.
- **Repainting less (0.8.9).** A heat map of the repaints on a three-monitor Lord Workspaces desktop showed 95–100 % of two displays repainted every 10 s with only small numbers changing, because one box was drawn around every change: a clock's seconds on one display and a network speed on another joined into nearly the whole desktop. Several damaged rectangles (`LORD_DAMAGE=multi` since 0.8.2) are now the default and also used when the GPU composes, each painted and uploaded on its own (`LORD_DAMAGE=one` goes back). A frosted node's blurred backdrop is kept per display and reused while nothing below it changes, so a clock hand inside a frosted widget is painted alone, and the margin a blur reads is what it really reads (45 px for the widgets' radius of 30, not 61). The Terminal compares each written row with what was drawn and damages only the cells that changed: a TUI's spinner frame repaints 0.2 % of the terminal (`term-damage-test`). `engine-test`'s damage fuzz and pipeline checks run with the blur cache on. On the same desktop, `lord-server` gives freed memory back at rest (`malloc_trim`, at most once a minute, never during a frame; its heap had been 277 MB with 216 MB in use), reads `/proc/cpuinfo` once, and a CPU figure is reported in steps of 1 %. Lord Workspaces' slideshow pans rather than zooms: on a 1080p display on the CPU each frame of the pan takes 9.6–10 ms against 52–53 ms for a 6 % zoom (`build/engine-test bench-slideshow`). No before-and-after measurement of a whole desktop is recorded for this edition.
- **Machines' picture and the desktop's pauses (in development after 0.8.9.4; `docs/MACHINES-GPU.md`, `docs/MAIN-THREAD.md`).** `lord-server` now reads each machine's frames in its own loop, acknowledges a frame right after the paint that showed it and repaints only the changed rectangle. On a Windows 11 guest drawing 61 frames a second (headless `lord-server`, CPU path, 60 Hz, two runs each): 29.5 → 60.0 frames a second shown, 1.7 → 0.1 ms of paint a frame, `lord-server` 54 % → 16–18 % of a core. With LordOS drawing the guest's pointer, a pointer move makes no frame; before, each move was a round trip through the guest (35–39 ms median). Monitor's process list on the screen's thread: 382 processes 4.0 → 1.3 ms, 1,900 processes 19.6 → 4.5 ms a call. Every JavaScript run over 50 ms is now logged with what it was; with Store, Settings and Files open, changing a setting went from 161 to 20 ms of frozen pointer and focusing a window from 241 to 31 ms, and a folder of 2,220 files opens in 229 ms instead of 1,986 ms (headless `lord-server`). Switches that start something slow, in Settings and the Store, flip at once with a spinner.
- **Cleaner (0.8.7; `docs/CLEANER-TESTS.md`).** On VM 116, with 122,000 files and a warm cache: a tree of 102,653 entries in 446 ms, duplicates in 5.1 s and a real delete of 20,000 files in 1.0 s. Paint figures are in §10.1.

### 7.3 GPU

On the VMs only a software renderer was available. With it, the CPU path is cheaper than "GPU" composition, which is why LordOS uses the CPU path when the only renderer is a software one. The GPU path's real benefit (composition and present close to free, zero-copy fullscreen) is expected on real cards. GPU composition runs on real Intel and AMD graphics (the author's RX 580 every day, and the community machines in [`docs/HARDWARE-REPORT.md`](https://github.com/lordbasex/LordOS/blob/main/docs/HARDWARE-REPORT.md), §3.2), but **its cost and benefit have not been measured on them yet**, and Nvidia cards are untested. Since 0.8.5 two tools report it on any machine: System Information shows each GPU layer and the exact reason when the screen is composed on the CPU, and the Test Bench draws a 3D scene with EGL and says whether the renderer is a hardware GPU, a virtual one or software (on VM 116: `llvmpipe`, software), with its draw time and whether its frames reach the screen without a copy.

### 7.4 The Raspberry Pi 5

The Raspberry Pi 5 and the Raspberry Pi 500 (a Pi 5 in a keyboard, with the same image, tested by a community member) are the supported boards. Results on a real Pi 5 (16 GB, SD card, without a monitor unless stated), from `docs/RASPBERRY.md`:

| Measurement | Value |
|---|---|
| Building every LordOS binary on the board | 1 min 02 s, 0 warnings |
| `make -C server test` (2026-10-18; not rerun on the Pi since) | 23 passed, 0 failed, 0 skipped |
| NEON blit and mask vs. plain C | 9.90 → 4.33 ms and 11.09 → 5.49 ms per screen (2.0–2.3×), bit-identical |
| Idle at the login screen, headless | `lord-server` 36 MB RSS, 0.6 % CPU; system 450 MB of 16 GB; 38–43 °C, no throttling |

| Building the LordOS kernel on the board | about 50 min per flavour |

**A desktop session at rest (0.8.8.9, 0.8.9 and 0.8.9.1; `docs/PERFORMANCE-0.8.9.md`).** The autologin session without a monitor, one hour after a reboot, sampled every 10 s:

| Version | `lord-server` RSS (median) | CPU, % of one core |
|---|---|---|
| 0.8.8.9, Lord Flow | 116 MB | 3.4 |
| 0.8.9, Lord Flow (two runs) | 113 MB | 6.1 |
| 0.8.9.1, Lord Flow | 113 MB | 6.2 |
| 0.8.9.1, Lord Workspaces | 99 MB | 0.06 |

0.8.9 uses 3 MB less memory and almost twice the processor, steadily in every 10 minutes and with nothing painted. 0.8.9.1's `lord-server` (on the 0.8.9 themes) changes neither on the Pi: the memory work freed caches of windows and of the Terminal's history, and this session has no monitor, no window and no Terminal. Lord Workspaces, measured on the Pi for the first time (the theme is now set with the session stopped, and the sampler checks it after the reboot), settles at 99 MB and 0.06 % of one core, so the extra processor at rest belongs to Lord Flow's theme, not to the server; finding it stays on the roadmap.

**The LordOS kernel.** The Raspberry Pi's own kernel doesn't build Landlock. Without it, the document-helper hostile test fails 5 of its 25 filesystem checks and the sandbox test can't run. LordOS builds the Raspberry Pi kernel from its own source and default configuration, changing only three options (Landlock on, the LSM list, the version suffix), and pins it so a newer archive kernel can't replace it. The image also enables the memory cgroup, which Raspberry Pi turns off at boot.

**Fans.** On the Pi 5 in a test case, `lord-fand` kept the fan off at 50–53 °C during a 4-thread load (the aluminium case acts as a heatsink), drove it to 55 % (4,500 RPM) and full speed (7,400 RPM) with test curves, and restored the kernel's own settings after `SIGTERM` and `kill -9` (`docs/FANS.md`).

**Monitor and image.** Since 0.8.4.1 the Raspberry Pi 5 image shows the desktop on an HDMI monitor at the first boot (the display driver line in `config.txt` now comes after the firmware's auto-detection lines, and LordOS waits up to 30 s for the driver), sets the clock from the network, and ships Chromium and Firefox ESR. Since 0.8.4 the LordOS Pi kernel (`6.18.57-lordos.3-rpi-2712`) also destroys the connections of a blocked app. **Measured on a monitor (LordBench, pre-release builds of 0.8.6):** the 0.8.5 image booted with a 1920×1080 60 Hz monitor on either HDMI port reaches the login screen 5.99 s after the kernel starts (systemd: 2.1 s kernel, 4.2 s userspace). With GPU composition (V3D) a window moved by the compositor keeps 59.4 frames per second, with a frame built in 10.9 ms (median) and 13.0 ms (99th percentile) and 1.0 % of frames late; under an all-core load at the lowest priority it falls to 24 frames per second with 96.5 % late, a problem LordBench found: the compositor's cgroup weighed the same as the load's, so the load's low priority did not count. Giving the compositor ten times the CPU weight of an app raised the same test, run without the monitor, from 43–45 to 56–57 frames per second (31–33 % → 7–8 % late) and brought a pointer move to the screen in 22 ms instead of 32 ms (median); with the monitor it was measured only together with the real-time priority below. The compositor's main and paint threads now also run at the lowest real-time priority, which lord-sessiond allows and lord-server drops before it starts anything, so no app inherits it; on VM 116 under load that took late frames from 2.7–2.9 % to 0.28 % and the slowest 1 % of pointer moves from 31–32 to 25 ms, as without load, with the load getting the same CPU time. On the Pi 5 with its monitor the two changes took the loaded test from 24 to 29–30 frames per second and the compositor no longer waits for a CPU, but under the load a frame takes 15–16 ms to build instead of 7, so it misses the 60 Hz refresh; that cause is still being looked for. LordBench's scene had a square meant to turn that stood still, because it was set through a style key the engine lacks; it now turns, which makes the test heavier: with it, that code showed 53–58 frames per second alone and 24–25 under the load. In 0.8.6 a dragged window's frame paints only what changed (the changed part of the window's layer and of what is below it), with the same pixels, checked frame by frame against recorded hashes; with that, the same test shows 59.8–60 frames per second alone (99th percentile 11.3–11.6 ms) and 30 under the load, where a frame is built in 12.9 ms (median) instead of about 20. Under the load nearly every frame is still late. A final pre-release run (2026-10-29) measured the two remaining changes. Composing the dragged window on the GPU passes its self-test on the Pi's GPU and gave the CPU's exact pixels in all 138 frames compared, but no measurable gain (30.8–31.6 frames per second under the load, against 30.5–31.1 without it). Painting the next frame while the previous one waits for the flip gave 33–36 frames per second under the load, but a pointer move reached the screen 17 ms later alone (42 instead of 25.5 ms, median) and 29 ms later under the load (78 instead of 49 ms). Both stayed in the code, off by default, in 0.8.6. With the final defaults the Pi 5 shows 59.9 frames per second alone and still goes from 60 to about 31 (30.5–31.1) under an all-core load. The remaining cost is the GPU's time per frame, which goes from 1.5 ms alone to 14–16 ms under the load, while the clocks and the temperature (36.7–47.2 °C) show no clock or thermal throttling; memory contention between the GPU and the busy cores was the likely cause, confirmed later (below). Sending and composing fewer pixels per frame, finding what slows the GPU under load, and composing the dragged window on the GPU for the whole drag (also where the Dock or the menu bar overlap it) moved to 0.8.7. The board's under-voltage alarm is present and read 0 with the official power supply. In a 3-minute all-core load with the fan the board kept 5.9 GFLOP/s at 55.6 °C at most, and it decodes 1080p video in software at 258 (H.264), 246 (HEVC), 204 (VP9) and 159 (AV1) frames per second.

**In 0.8.7, measured on the same board on development builds (2026-10-31; `docs/GPU.md`).** *What slows the GPU under load is memory.* `build/gpu-contention` (two runs on the Pi 5 16 GB) gives a GPU time per frame of about 1.4 ms with all four cores spinning, 28 ms with four cores reading memory and 3.7 ms with four cores writing, with the V3D clock at 1.15 GHz, no throttling and at most 44 °C. Which reads a real desktop load does, and how much a change in the compositor can avoid, is still open. *GPU drag now covers the whole drag and is on by default.* The menu bar or the Dock in the damaged box used to refuse nearly every frame of a real drag; now they only shorten the window's rectangle. In 4 real 16-second drags of each setting on its monitor, alone the session's CPU fell from 58.1–60.6 % to 27.2–28.4 % of a core and the work per frame from 7.0 to 5.0 ms; under a memory load of four `dd` processes, 28.8–29.1 frames per second became 34.4–35.1, 20.3 ms became 13.2 ms and 67 % became 45 %. `LORD_GPU_VERIFY=1` compared 1,662 frames, all with no pixel different. LordBench's Desktop impact doesn't see the gain, and pointer latency doesn't change. It costs a self-test of about 350 ms at the start of each user session (none at the login screen) and 0.6 ms more of GPU a frame in a drag. **It is verified on V3D and SVGA3D only:** on a VMware virtual machine with SVGA3D, `LORD_GPU_VERIFY=1` compared 2,102 frames, all with no pixel different, and the session's CPU in a drag over a clear area fell from 7.5–7.7 % to 3.9–4.3 % of a core, with a smaller gain across the Dock and none for a tall window that the menu bar and the Dock keep refusing there. On any other GPU only the self-test guards it, and `LORD_GPU_DRAG=0` turns it off. *The buffer-age scissor stays off:* on the Pi 5 (5 runs without it, 3 with it) the GPU's part rose from 1.51 to 2.58 ms alone, and under load 30.1–31.8 frames per second fell to 28.4–29.9 and the pointer's 99th percentile rose from 63–66 ms to 83–95 ms.

**In the released code.** GPU drag is declined while a Linux window is on screen. In the last pass (v087.27) the virtual machine with SVGA3D compared 2,172 frames, none different; it did not run the final v087.28, whose changes are in the shell, not in GPU drag.

**Moving wallpapers (0.8.7; `docs/WALLPAPERS.md`).** On the Pi 5 at the login screen, playing 1080p at 60 fps:

| Case | Result |
|---|---|
| H.264, software decoding, CPU composition (a trial build) | about 156 % of one core |
| HEVC, hardware decoding, GPU composition (0.8.7) | `lord-media` 41 %, `lord-server` 147 % of one core, over 30 s, SoC at 52 °C in its case |

Decoding is in hardware, but each frame is then read back and converted to BGRA in `lord-media`, and `lord-server` paints it; that copy is why the total stays high. Showing the decoder's buffer directly on the GPU did not make 0.8.8 and is planned for a later release. No run on a desktop session is recorded.

### 7.5 Modern PCs

No LordBench reference for a real PC is in the repository yet; the real-PC numbers in this paper come from the author's PC during 0.8.8.6's development and were taken once (§5.1, §7.1), and for 0.8.9 and 0.8.9.1 from session measurements on the same PC with `tools/bench/session-sample.sh` (§7.1, `docs/PERFORMANCE-0.8.9.md`), and two community hardware reports include a LordBench quick run (#136, #156). The project tests the ISO on virtual machines (UEFI and BIOS); on real hardware, community reports show LordOS installed on 17 machines (internal disk or eMMC) and run live from a USB stick on one, AMD machines with an RX 580 and an RX 9060 XT among them ([`docs/HARDWARE-REPORT.md`](https://github.com/lordbasex/LordOS/blob/main/docs/HARDWARE-REPORT.md)). LordBench (0.8.6) is designed to measure memory and CPU at idle, boot time, frame times, video and app start in a repeatable way, and community hardware reports (0.8.7) to collect them from real machines (`docs/BENCHMARK.md`). 0.8.6 ships its first part: a sandboxed `lord-bench` helper that measures the CPU, memory, the GPU offscreen, storage and a sustained load, stops near the temperature limit or when the processor throttles, and records the conditions of each run, shown in System Information → Performance as "×N" of reference machines; it also measures software video decoding and the remote desktop's encoders, the desktop's frame times and the time from a pointer move to the screen, alone and under a low-priority load, and boot time over several restarts (run on the Pi 5 with 3 boots of 7.6–7.7 s, started without the app's button); it also runs from a terminal (`lordos-sysreport bench`). It also times LordOS's own interface work with the engine's real code (the layout and paint of a fixed full-HD desktop scene, and the shaping of paragraphs in Latin, Arabic, Devanagari, Thai and Chinese with fonts built into the helper, which opens no files; on the reference virtual machine 37 frames per second on one core and 40 with the paint threads, 619 shaping runs per second on one core and 3,595 on eight; on the Raspberry Pi 5, in a full run that is now part of its reference, 39 and 45 frames per second and 628 and 2,514 shaping runs per second on one and four cores, within 0.6 % of two earlier quick runs), compared with a reference only when it was measured with the same LordOS version, and `lord-bench` checks its own sandbox before any work: six things it must not be able to do (open a local socket or a network connection, run a program, start a process, create a file, read a system file) were all refused on that machine, and a run where one gets through is marked unstable. On a Raspberry Pi it watches the board's firmware during the whole run: the under-voltage alarm, the only flag the LordOS Pi kernel exposes, the firmware's full throttling flags where an older kernel has them, and 80 °C, where the firmware starts slowing the processor down, which stops a peak test as throttled; System Information's Raspberry Pi section reads the same alarm and flags and leaves out what the kernel doesn't show. This was tested on simulated system files and on the Pi 5, where the alarm is present and reads 0 with the official power supply; an actual under-voltage was not provoked. The references are a virtual machine and a Raspberry Pi 5 (§7.4); hardware video decoding and a real PC reference were not built in 0.8.6 and moved to 0.8.7. In the 0.8.7 release the x86 PC reference is still to be chosen and LordBench's video workloads still have no hardware decoding; the Raspberry Pi 5's HEVC decoder reached `lord-media` for moving wallpapers (§7.4).

## 8. Visual experience

- **A design guide.** Apps follow a shared guide (`docs/DESIGN.md`): an 8 px spacing grid, a small type scale, consistent control heights and one accent-coloured action per view. The tokens are exported by the SDK (`spacing`, `typeScale`, `controlSize`), and every app went through documented before-and-after polish passes in light, dark, right-to-left and small windows.
- **Themes.** A theme is a complete desktop written in React: menu bar, Dock, app launcher, Control Center and window frame, plus its tokens. LordOS ships **Lord Flow**, with a menu bar and a Dock, and since 0.8.3 **Lord Classic** as a second full appearance: a taskbar, a start menu with search, a tray, quick settings, a notification panel, window snapping with layouts, and its own restyling of every app. Both have window snapping and, since 0.8.7, Desktops with a shared Overview: a window on a hidden desktop never has the keyboard, which the compositor enforces for fullscreen too (`docs/DESKTOPS.md`). Themes switch live; settings persist. Since 0.8.8.7, Settings → Desktop & Dock → Window buttons puts close, minimize and maximize on the left or the right in either theme (Automatic keeps each theme's side), and Linux apps that draw their own title bar get the same side (#58). In 0.8.5 the two themes took these names (formerly "Default" and "Classic"; the user's choice is kept), Settings → Appearance → Desktop style became the one place that lists every installed theme, and if a theme is refused the last theme that loaded stays the fallback. **In 0.8.9** a third theme, Lord Workspaces (below), ships too, and the first session of a new account on an installed system opens a three-step chooser in the language picked in the installer: three equal cards for Lord Flow, Lord Classic and Lord Workspaces, each with a real picture, in a random order with none chosen or marked as recommended; the chosen desktop is applied live in a small floating box with Back and Use this; then a drawn replica of Settings → Appearance shows where to change it (`sdk/firststart.jsx`, `sdk/firststartmodel.js`; docs/SETTINGS.md, "First start"). It never shows on the live system, the OVA's first boot, the login screen or to anyone who already used LordOS (settings migration 6), and once done it leaves no listener or timer. Tests: `firststart_model_test.mjs` (51 checks) and `firststart_scene.mjs` over each theme (33 checks each), headless; not yet seen on a real first start. Desk widgets now work in every theme (§5.1).
- **Lord Workspaces (0.8.9; `docs/WORKSPACES.md`).** A third theme, approved on 15 November 2026, that organizes the desktop by activities: each activity is one of the desktops above (up to 9) with a name, an icon, a colour, pinned apps and a layout per display, kept in a new settings key with when each was last changed; up to three more groups inside one activity, on the same desktop, make 36 activities with no tenth desktop faked. A strip of pills switches them, and resting on another activity's pill shows what it holds (the Focus Surface). A Context Spine (the crown's system menu, Activities, Apps, Files, the Control Center, the shortcuts' help and Settings) replaces the menu bar and the Dock; each display has a group frame with static tiling (free, one at a time, two halves, main and side, three columns, grid), a divider applied on release, a padlock that locks that display's windows, drag to swap tiles or to another monitor's tiles, a flyout of halves, thirds and quarters on the maximize button, and Save layout, which remembers which app goes in which tile of which monitor, keyed by connector, and falls back to the main display when a monitor is missing; one activity spans every display, and an app opens on the display it was asked from. Its own Search panel adds Activities and Open windows to LordOS's search. The Control Center becomes the Control Atlas, with sections for appearance, the tiling of the activity in view, activities, displays, sound, network, energy and security, each title opening its Settings page. A high-contrast mode (Settings → Appearance and the Control Atlas) gives solid black or white surfaces, text at 21:1, dim text and the accent at 7:1 or more, a line round every surface and no blur or shadows (the ratios are checked by `workspaces_model_test.mjs`). ⌃F2 moves the keyboard to the spine and the activity strip, even over a Linux app, through a key table of its own in the compositor (`workspaces` in `wl/keygrab.c`: Lord Flow's plus ⌃F2 and ❖1…9; Lord Flow's own table is unchanged). Every surface takes one of three effects styles, Opaque, Translucent or Crystal (glass with a sheen from the top and a depth shadow), with one live blur at rest (the spine). Its default accent is pink and its default wallpaper Cyberpunk City HD's panorama: the saved default accent and wallpaper now mean "the theme's default" (`null`), so Lord Flow and Lord Classic keep blue and Lumo Celestial; it also offers the design proposal's amber, has its own pointer in the accent colour (§3.3) and, in Settings → Wallpaper and only here, a slideshow, off by default, that goes through a category every 1, 5, 15 or 30 minutes or every hour, with a different picture on each display if chosen, a 2.4 s cross-dissolve with a pan (a plain 0.4 s crossfade with Reduce motion), the next picture decoded 8 s ahead by `lord-server`'s image workers, and no change while nobody sees the screen, in the power-saving mode, on a low battery or on a display hidden by a window; it was checked on stub displays only, not on real monitors or the GPU path; on the maintainer's three monitors it cost `lord-server` 19.0 % of one core, against 2.0 % with it off (§7.1). Its transitions run on cached transforms from one frame loop and stop with Reduce motion. Settings now reads a theme's `theme.json` for its picture, its own options, its default wallpaper and the slideshow (`sdk/thememeta.js`); Lord Flow and Lord Classic are unchanged. Measured in headless sessions at 1920×1080 on the CPU path against the other two themes in the same scenario: focus changes repaint about a third of the screen they do, activity switches cost about as much as their desktop switches (192 native calls for four switches instead of 352 in `theme_cost_scene.mjs`), and no timer runs every second at rest. Checked with scene tests on three displays and headless screenshots. On the maintainer's own computer (three monitors of one model, GPU composition) a test build froze the desktop when Google Chrome opened or the Apps panel did; not reproduced yet, it brought two fixes (the displays are keyed by their connector, not their model's name, which three identical monitors share; the tiler asks a window for a tile's size once per tile and keeps the size the app answers with, at most 10 moves per window and 60 passes per second) and a watchdog in the compositor: a main loop away from its poll for more than 2 s drops the real-time priority for the rest of the session and logs the main thread's state with its C and JavaScript stacks, and a JavaScript task still running after 10 s is stopped while the desktop goes on (`wdog.c`, `build/wdog-test`). The same work found that the real-time demotion had always left the main thread at real time (the kernel refuses to clear `SCHED_RESET_ON_FORK` without a privilege); it keeps the flag now. Not yet checked on right to left; on real monitors and the GPU path only on the maintainer's own computer with test builds. Live miniatures of hidden activities, real frosted glass over Linux apps on the GPU and a different activity per monitor are left for the compositor and the SDK.
- **Lord Workspaces: each display's apps, in development after 0.8.9.4 (`docs/WORKSPACES.md`, "Several displays"; `CHANGELOG.md`, Unreleased; not in the latest release).** The SDK keeps, per display by connector, the apps opened there and the apps open there together, in tile order with the layout (`sdk/displayapps.js`, for every theme): at most 8 displays, 12 apps and 6 sets each, use that halves every 14 days and is forgotten after 90, on this computer only. In Lord Flow, clicking the app's name in the menu bar opens its app menu (About the app with its own version, its Settings, Hide, Hide Others, Show All, Quit), and the crown menu adds the Store with the number of waiting updates, Recent Items and Force Quit… (§5.4). Transparent apps such as the Terminal get an opaque border and title-bar line.

Since 0.8.9 the accent nobody chose is the theme's own (blue in Lord Flow and Lord Classic, pink in Lord Workspaces), and Linux apps get its name through the portal.
- **Right to left.** The whole interface mirrors for Arabic, Hebrew and similar scripts, including isolated apps, which follow the session's language live.
- **Lumo.** LordOS's mascot is Lumo, a small celestial fox, used in welcome screens, empty states and brand material, with a fixed set of poses defined in the brand guide.
- **Accessibility today:** a "reduce motion" setting that turns off decorative animations, keyboard shortcuts throughout, scalable displays up to 200 % (300 % since 0.8.8.6), in 0.8.7 an on-screen keyboard that also works at the login and lock screens, and, since 0.8.8.6, reading the selection aloud anywhere (❖Esc), Live Speech to say what is typed (❖⇧Esc), a Personal Voice made from the user's own, and shaking the pointer to find it. In 0.8.9 Lord Workspaces adds a high-contrast mode (above), and the Overview moves between rows of windows with Up and Down in every theme. A screen reader, zoom and a high-contrast mode for Lord Flow and Lord Classic are on the roadmap and **not built yet**.

## 9. Extensibility

- **The SDK** (`@lordos/sdk`) is the only thing apps import: windows, settings, theme tokens, controls, files, media, notifications, keyring, printing and more. Apps don't import from themes, so any app works in any theme.
- **Writing an app** means a folder with `manifest.json` and `index.jsx`. `node tools/lpk.mjs <folder>` bundles it without React or the SDK, adds the icon and translations, and signs it if a key is given; `keygen`, `sign`, `verify` and `catalog` cover the rest. Apps can include WebAssembly modules and draw raw pixels with `<Image pixels>`.
- **Themes** follow a fixed contract (`Desktop`, `MenuBar`, `Dock`, `Launcher`, `ControlCenter`, `WindowFrame`, tokens), documented in `themes/README.md`, with the Lord Classic theme as a template. Since 0.8.5 `docs/THEMES-GUIDE.md` explains, for a React developer new to LordOS, a theme's parts (theme.json, tokens, the shell, window frames, menus, layers), right-to-left, light and dark, several displays and the performance rules, with a checklist, and `examples/theme-minimal/` is a small working theme to start from. Since 0.8.9 a theme's `theme.json` may also declare its picture in Settings (`sketch`), its own options (`options`, kept in the `themeOptions` settings key), `desktopArrows`, a default wallpaper and a slideshow, all checked strictly by `sdk/thememeta.js`, and the SDK gives every theme the widget catalog, the first-start chooser and per-display wallpapers. A theme LordOS didn't sign doesn't load on a release build yet: there is no theme package format or user trust decision.
- **Linux interoperability** is through standards: Wayland, the Settings and FileChooser portals, the Secret Service, the notifications service, `mimeapps.list` default apps and `.desktop` files.
- **Automation:** there is no scripting or automation API beyond the SDK today. Since 0.8.5 the Store installs AI apps (§5.3), but they are ordinary Linux apps with the same rules as any other; integrations of AI assistants with the desktop itself (for example through the Model Context Protocol) **do not exist in LordOS**; they are only a possible future direction and would have to respect the same rule that JavaScript can't execute commands.

### 10.2 Known limitations

- Real hardware is known from 22 physical machines (the author's PC, §3.5; nine community hardware reports; twelve machines named in other issues), with 14 Intel and 4 AMD GPUs and 4 not stated, 17 Intel and 2 AMD CPUs, 14 laptops, 3 desktops and 4 tablets or 2-in-1s, plus 4 virtual machines ([`docs/HARDWARE-REPORT.md`](https://github.com/lordbasex/LordOS/blob/main/docs/HARDWARE-REPORT.md), compared there by GPU, CPU, kind, boot medium and version). Nvidia GPUs, AMD integrated graphics, Intel graphics newer than Whiskey Lake, DisplayPort hubs, suspend and resume (unchecked in every report), printers and scanners, FIDO2 keys and real mail providers are untested. Open problems found on that hardware are listed there, among them Cherry Trail tablets' sound and charging; their volume and power buttons and a mouse's back and forward buttons have fixes in 0.8.8.9, not yet tried on that hardware.
- In 0.8.9: Lord Workspaces has been checked in scene tests, headless sessions and the maintainer's own test builds, not on right to left, and its slideshow only on stub displays (not on real monitors or the GPU path); the freeze seen on the maintainer's three monitors is not reproduced and its cause is unknown (the watchdog would name it); Settings → Battery and its charge control have not been tested on laptop hardware, nor the lid hook on the reporter's laptop (#172); the 75 % and 80 % scales have not been checked on the VM or a real 1280 × 800 laptop; `lordos.service`'s restart with sessions alive has not been run on systemd 258 or later (Debian 13 ships 257); the first-start chooser has run in scene tests only; `lord-hidpp` was tried with the maintainer's MX Master 3 and MX Keys only; `lord-stream` was checked against local FFmpeg servers, a webcam served over RTSP by VLC and a public HTTPS HLS stream and list, it has no ONVIF discovery, and an rtsps camera's certificate can't be checked with FFmpeg 7.1 (§6.7).
- Machines' work in development after 0.8.9.4 (§5.1) was checked on one amd64 PC with KVM, mostly through `lordvm-dev`, a development tool that plays `lord-server`'s part, not yet all inside `lord-server`'s window: apps mode has not been seen drawing on a real display, and the sound and network panes of Configure not on screen. Windows machines are 2D only and amd64 only (arm64 is a later stage), and need the person's own license; Microsoft may change what its documented install settings allow. In a Windows machine every account can read a dropped file while it passes through the transfer folder: for machines several people use, turn the folder off and files go through the guest agent. A bridged machine's traffic isn't seen by LordOS's firewall, and a running 3D machine can't be suspended or snapshotted with its memory.
- In 0.8.8.9: the tablet power-button defaults have not been tried on a tablet (the live session on one still shuts down on a tap), mounting a free partition of the system disk has not run on a real dual boot or a hibernated NTFS volume, Control Center's brightness slider has not driven a real backlight, a web app's Browser identity, offline page and developer tools have not been checked on screen, and each image's source list has not yet been written for a LordOS image.
- The Raspberry Pi 5 and the Raspberry Pi 500 (the same image, tested by a community member) are the supported boards, with LordOS's build of the kernel with Landlock; its 0.8.5 image was booted and used on a 1920×1080 monitor on both HDMI ports; other monitors and resolutions are untested.
- Linux apps are not sandboxed by default. X11 apps need Debian's `xwayland` package.
- Firewall: no ask mode; domain rules don't see apps that resolve names with their own encrypted DNS.
- Restrictions for Linux apps don't cover BlueZ over D-Bus, the system bus, the clipboard or apps started outside the app launcher; the `user@` union also holds the user's own services while a restricted app runs; a new PipeWire client has a window of a few milliseconds before the guard restricts it (§6.6).
- The `.lpk` signing key is still a development key, and there is no signed repository for `.lpk` apps yet.
- Permissions: no "allow once"; camera and microphone use by Linux apps isn't shown.
- Secure Boot must be turned off; signing with a shim is pending.
- Steam and the engine's i386 multiarch (0.8.8.9) have been tried on one LordOS system only, the maintainer's PC with an AMD Radeon RX 580 (Vulkan through RADV, Mesa 25.0.7), where Lost Ark, a Windows game, ran through Proton; Valve's `steamdeps` may still ask to update apt's lists on Steam's first start.
- AI apps on a GPU: llama.cpp's Vulkan backend is untested on real AMD, NVIDIA and Intel hardware.
- On the Raspberry Pi 5 an app keeping every core busy still halves the desktop's frame rate (about 31 instead of 60 frames a second in LordBench's test): the GPU's time per frame grows under the load, and the two changes measured for it in 0.8.6 gave too little and are off by default. In 0.8.7 the cause found is memory reads, and GPU drag takes a real drag under a memory load from 29 to 35 frames per second, still far from 60 (§7.4).
- GPU drag (0.8.7) is verified on V3D and SVGA3D only; on any other GPU only its self-test guards it (§7.4). It is declined while a Linux window is on screen.
- Files → Network (0.8.7): SMB with a password passed against one real share on a desktop system and one test server, no others; no real NFS server has been tried; listing the shares of an SMB server outside the local network is refused (§5.1).
- Remote Desk (0.8.7): VNC and RDP were run against a throwaway test machine; RDP to a real session of a desktop system and RDP's shared folders have not been verified in a real session. VNC traffic is not encrypted (§6.7).
- A self-signed certificate on a connection must name the host it's used for.
- Moving wallpapers copy each frame on its way to the screen (§7.4); a zero-copy path did not make 0.8.8 and is planned for a later release. The Pi 5's hardware decoder handles HEVC only, so H.264, VP9 and AV1 clips don't play there.
- Screen sharing (0.8.8): on a Raspberry Pi 5, a video playing while the screen is shared drops frames (AV1 at 1080p: 0.5 % without sharing, 36 % in a short sample); while an app shares the screen, Linux apps can't go full screen.
- Install in free space (0.8.8) ran to the end only in a virtual machine whose other system was a test file (#7): starting a real second system beside it has not been tried by the project; one community laptop runs LordOS next to another system (#129, [`docs/HARDWARE-REPORT.md`](https://github.com/lordbasex/LordOS/blob/main/docs/HARDWARE-REPORT.md)) (§5.6).
- Administrator rights for Linux apps (0.8.8): only `pkexec` is covered, and programs that ask polkit over D-Bus still find no agent; the prompt takes a physical keyboard only, and its three-try limit is untested.
- The OVA (0.8.8): the first account, the restart and the login were tested in VirtualBox; the same steps passed in VMware Fusion. The arm64 ISO and the Raspberry Pi image of 0.8.8 were built and ship, but were not booted for this release.
- French (0.8.8) is a first translation with no native review, sizes still read GB and MB, and French, Italian (0.8.8.2) and Lithuanian (0.8.8.7) have no Help articles yet. The 29 languages new in 0.8.8.9 are complete but have had no native review yet (native speakers are invited to confirm them or report mistakes through a [translation review](https://github.com/lordbasex/LordOS/issues/new?template=translation-review.yml) issue) and no Help articles, and Persian and Thai dates are Gregorian (no Solar Hijri or Buddhist calendar).
- The Terminal's Files mode (0.8.8.7) doesn't share an `ssh` opened before this version or one made from inside another server.
- The Terminal's port forwards, uploads by dropping files and downloads from `ls` (0.8.8.8) were checked against one private OpenSSH server in a real session; other servers are untested, and a forward only brings a server's port to this computer.
- Databases (0.8.8.7) speaks MySQL and MariaDB only (through an SSH tunnel since 0.8.8.8); IAM tokens, editing relations and triggers, users, processes, import and export come in a later phase (`docs/DATABASES.md`).
- A cloud account signed in with a password and a device code may ask for the code again after every logout or restart: the provider refuses the kept session when rclone starts again (rclone's issues 9658 and 9966, with fixes proposed and not released). LordOS says so, no longer retries such an account by itself, and offers a log for rclone's issue with names and tokens taken out.

- The arm64 live ISO has run on emulated QEMU only: the signed release ISO reached the live desktop, and an unsigned development build installed to disk: real hardware, a USB stick, a hypervisor with hardware acceleration, a 3D virtual GPU, sound, the browsers and a signed build are not tested (§5.6).

- Window memory across two displays is not tested; session restore doesn't reopen a Files folder (§3.6).

- The volume, mute, brightness and keyboard light keys (0.8.8) were confirmed on two MacBook Pros by the people who reported them (#12, [`docs/HARDWARE-REPORT.md`](https://github.com/lordbasex/LordOS/blob/main/docs/HARDWARE-REPORT.md)); other laptops' keys are not recorded. - X11 apps on HiDPI (0.8.8.8): the scale doesn't follow a display change while X11 apps are open, and an app that reads neither `Xft.dpi` nor a setting of its own toolkit looks small.
- Web apps (0.8.8.8): `lord-web` runs on VM 127, where the light and dark mode, the Store's install and an app's own window were checked; of the 37 apps in the catalog, only one chat app is marked tested on LordOS. - logind's `Unlock` is not obeyed (0.8.8.8): only the login screen's password unlocks.
- Without a GPU, AV1 video at 60 fps is heavy, since the browser decodes it in software on the same machine.
- Accessibility: a screen reader and zoom are not built, and high contrast exists only in Lord Workspaces (0.8.9).

## 11. How to verify the project yourself

### 11.1 Build it

On a development machine with Node.js, bundle the themes, SDK and apps:

```
npm install && npm run build
```

On Debian 13, build the binaries and run the tests:

```
sudo apt-get install -y --no-install-recommends build-essential
make -C server -j4
make -C server test        # every self-contained suite
make -C server test-full   # adds the helpers, the sandbox and the HarfBuzz comparison
```

`make test` fails if any suite fails; a suite whose tool or data isn't installed reports "skipped" rather than passing silently. The sandbox tests need a kernel with Landlock. The ISO and the Raspberry Pi image are built as described in `docs/ISO.md` and `docs/RASPBERRY.md`. On VM 116 with the 0.8.5 tree: 23 passed, 0 failed, 10 skipped (the Node.js suites, which run on the development machine).

### 11.3 Check a release

Download `SHA256SUMS`, `SHA256SUMS.sig`, the release files and the public key (`tools/release/lordos-release.pub.pem`). Check that the key's fingerprint is `c7155b8e6bbbb180f907381994d06af76d333016cd6f3facf67cadd053ea108e`, then, with OpenSSL 3:

```
base64 -d SHA256SUMS.sig > SHA256SUMS.sig.bin
openssl pkeyutl -verify -pubin -inkey lordos-release.pub.pem -rawin -in SHA256SUMS -sigfile SHA256SUMS.sig.bin
sha256sum -c --ignore-missing SHA256SUMS
```

The SBOM of each architecture (`lordos_<version>_<arch>.spdx.json`) is listed in `SHA256SUMS` too, so the same check covers it.

### 11.4 Check a running system

- `systemctl status lord-netperm lord-fand lordos` shows the services; the ISO test confirmed the seven network programs attached. If the kernel refuses the device or the LSM program, `lord-netperm` reports `"devices":false` or `"bluetooth":false`.
- `cat /proc/<pid>/status | grep -E 'Seccomp|NoNewPrivs'` on a `lord-server --app` process shows the sandbox.
- `systemd-cgls` shows the root-owned `lordos-session-<uid>` tree with one scope per app.
- Remote desktop: `ss -ltn` shows nothing on port 5673 until you enable it in Settings → Sharing.
- **System Information → Checks (0.8.5)** does these checks for you and says whether each was found configured or actually tried: the display server without root, Landlock, the per-app firewall with its kernel pieces, every bundle of LordOS's own code verified this session, the remote desktop's port closed when it is off (read from `/proc/net`), the session's cgroup tree owned by root, composition on the GPU, and **Run tests** for the Sandbox Probe (§6.4).
- **`lordos-testbench --auto`** prints a JSON report of the Wayland checklist, frame and presentation timing, the 3D renderer and input-to-screen latency; `lordos-sysreport report --json` prints the hardware report without serial numbers, addresses or names.

## 13. Glossary

- **Broker:** the single socket through which an isolated app asks `lord-server` for anything that touches the user's things; every request is checked in C.
- **cgroup (v2):** a kernel mechanism that groups processes to account for and limit resources. LordOS gives each app its own group, a "scope", and uses it to identify the app in the firewall.
- **Compositor:** the program that combines the windows of all apps into the final image on screen.
- **DRM/KMS:** the kernel interfaces for graphics devices and for setting display modes.
- **eBPF:** small verified programs that run inside the kernel; LordOS attaches them to cgroups to decide network connections, device opens and Bluetooth sockets.
- **evdev:** the kernel interface for input devices.
- **LSM (BPF LSM):** the kernel's security hooks; with the `bpf` LSM, a small program attached per cgroup can refuse an operation, such as creating a Bluetooth socket.
- **Namespace:** a kernel feature that gives a process its own view of something (users, mounts, process ids); LordOS uses unprivileged ones for Linux apps restricted from the user's files.
- **Helper:** a small LordOS process that handles untrusted data or secrets in a stricter sandbox (`lord-doc`, `lord-media`, `lord-maild`, `lord-vault`, `lord-fetch`, `lord-tls`, `lord-bench`, `lord-clean`, `lord-lan`, `lord-rdesk`, `lord-ocr`, `lord-tts`, `lord-sftp`, `lord-sql`, `lord-screencast`, `lord-vmdisplay`, and in 0.8.9 `lord-stream` and `lord-hidpp`).
- **Landlock:** a kernel feature that lets an unprivileged process restrict which files and network ports it, and its children, may use.
- **`.lpk`:** LordOS's package format for installable native apps.
- **`.lvault`:** LordOS's encrypted vault file format.
- **PipeWire guard:** `lord-server`'s own PipeWire client that hides capture devices from restricted Linux apps and stops their capture streams.
- **Powerbox:** a file dialog drawn by the system that hands the app only the file the user chose.
- **QuickJS:** a small JavaScript engine written in C.
- **SBOM:** a software bill of materials, the machine-readable list of the components a release contains, in the SPDX format.
- **Scope:** a cgroup for one app, such as `app-lordos-lpk-<id>.scope`.
- **seccomp-bpf:** a kernel filter that restricts which system calls a process may make.
- **Secret Service:** the freedesktop D-Bus standard Linux apps use to store secrets.
- **Wayland:** the protocol between graphical apps and the compositor.
